= KonfPlan: Migration lokal mit PROD-Daten testen (ohne PROD zu gefährden)
:toc: left
:toc-title: Inhalt
:toclevels: 2
:icons: font
:sectnums:

Diese Anleitung beschreibt, wie eine neue Flyway-Migration (hier als Beispiel: `V28__gruppenkategorien.sql`, Feature #690) vorab lokal gegen eine Kopie der echten PROD-Datenbank getestet und überprüft werden kann - ohne die produktive Datenbank selbst anzufassen. Das Verfahren ist unabhängig von der konkreten Migration und kann für künftige Migrationen wiederverwendet werden.

[WARNING]
====
Der erzeugte Datenbank-Export enthält echte personenbezogene Daten (Namen, E-Mail-Adressen, Schulzugehörigkeit von Teilnehmern). Die Export-Datei nur lokal und temporär aufbewahren, nicht ins Repository committen, nicht in Cloud-Speicher oder Chats hochladen, und nach dem Test sicher löschen (siehe Schritt 6).
====

== 1. PROD-Datenbestand exportieren (rein lesend, unkritisch)

Im Organisator-Dashboard auf PROD als *Administrator* anmelden, Tab *"Datenbank-Export"* öffnen und *"Backup herunterladen"* klicken.

Dahinter steckt `GET /api/administrator/backup/export` (`DatabaseBackupResource.java`), das serverseitig einen `pg_dump -Fc` (Postgres-Custom-Format) ausführt und als ZIP liefert:

[cols="1,3",options="header"]
|===
| Datei im ZIP | Inhalt
| `konfplan.dump` | Vollständiger Dump der KonfPlan-Datenbank
| `keycloak.dump` | Vollständiger Dump der Keycloak-Datenbank (für diesen Test nicht benötigt)
|===

Dieser Export ist ein reiner Lesevorgang - er verändert PROD nicht.

== 2. Lokale, isolierte Postgres-Instanz starten

Das Repo bringt dafür bereits ein Skript mit, das eine Wegwerf-Postgres-Instanz mit derselben Major-Version wie PROD (`postgres:18`) startet:

[source,bash]
----
cd /Users/kreyj/Java/berufsorientierung/KonfPlan
DB_PASSWORD='ein-wegwerf-passwort' ./db/ensure_prod_db.sh
----

Ergebnis: Container `konfplan_prod` mit leerer Datenbank `konfplan` auf `localhost:5432` - unabhängig von der Dev-Datenbank.

== 3. PROD-Dump in die lokale Instanz einspielen

[source,bash]
----
unzip konfplan-backup_*.zip -d /tmp/konfplan-restore
docker cp /tmp/konfplan-restore/konfplan.dump konfplan_prod:/tmp/konfplan.dump
docker exec -i konfplan_prod pg_restore -U postgres -d konfplan --clean --if-exists /tmp/konfplan.dump
----

Die Datei `keycloak.dump` wird für diesen Test nicht gebraucht.

Die lokale Instanz enthält danach exakt den aktuellen PROD-Stand - inklusive der `flyway_schema_history`, also allem *bis, aber ohne* die zu testende neue Migration (da diese in PROD noch nicht ausgerollt ist).

== 4. Migration anwenden und Ergebnis prüfen

[IMPORTANT]
====
Die beiden folgenden Wege (4a: nur SQL, 4b: komplette App) schließen sich auf **derselben** wiederhergestellten Kopie gegenseitig aus: Wendet man die Migration erst manuell per `psql` an (4a) und startet danach die App (4b), versucht Flyway dieselbe Migration ein zweites Mal auszuführen - das schlägt mit `relation "..." already exists` fehl, weil Flyway von der manuellen Anwendung nichts weiß (`flyway_schema_history` wurde dabei nicht aktualisiert). Vor einem Wechsel von 4a zu 4b daher **Schritt 3 (Restore) erneut ausführen**, um wieder beim PROD-Stand ohne die neue Migration zu starten (siehe Hinweis am Ende von 4a).
====

=== 4a. Schneller Weg: nur die SQL-Datei anwenden und per psql prüfen

Es gibt in diesem Projekt kein Flyway-Maven-Plugin - Flyway läuft ausschließlich als Quarkus-Runtime-Extension beim App-Start (`%prod.quarkus.flyway.migrate-at-start=true`). Für einen reinen Migrations-Test reicht es, die SQL-Datei direkt anzuwenden:

[source,bash]
----
docker exec -i konfplan_prod psql -U postgres -d konfplan \
  < backend/src/main/resources/db/migration/V28__gruppenkategorien.sql
----

Anschließend interaktiv prüfen:

[source,bash]
----
docker exec -it konfplan_prod psql -U postgres -d konfplan
----

[TIP]
====
Tabellennamen in Postgres sind hier klein geschrieben (`gruppenkategorie`, nicht `"Gruppenkategorie"`) - Hibernates physische Namensstrategie in diesem Projekt lowercased alle unquoted Identifier. Mit `\dt` in `psql` die tatsächlichen Namen prüfen, falls unsicher.
====

Beispiel-Prüfabfragen für die Gruppenkategorien-Migration (analog für andere Migrationen anpassen):

[source,sql]
----
-- Übersicht der angelegten Kategorien
select veranstaltung_id, name, mehrwertig, pflicht from gruppenkategorie;

-- Werte je Kategorie
select gk.name, gkw.wert from gruppenkategoriewert gkw
  join gruppenkategorie gk on gk.id = gkw.gruppenkategorie_id
  order by gk.name, gkw.wert;

-- Werte, die KEINEM der drei Muster entsprechen und daher nicht migriert wurden
-- (laut Annahme sollte diese Abfrage keine Zeilen liefern)
select distinct tg.gruppen from teilnehmer_gruppen tg
  where tg.gruppen not in ('RKS','MGL')
    and tg.gruppen not like 'M\_%'
    and tg.gruppen !~ '^[0-9]';

-- Plausibilitätscheck: Anzahl migrierter Zuordnungen vs. Ausgangsdaten
select count(*) from teilnehmer_gruppenwert;
select count(*) from teilnehmer_gruppen;

-- Bestätigung der akzeptierten Einschränkung aus Slice 1: kein Teilnehmer sollte
-- aktuell in mehreren Veranstaltungen gleichzeitig Mitglied sein
select nutzer_id, count(*) from nutzer_veranstaltung
  group by nutzer_id having count(*) > 1;
----

Danach für 4b wieder bei PROD-Stand starten (falls gewünscht):

[source,bash]
----
docker exec konfplan_prod psql -U postgres -d konfplan -c "DROP SCHEMA public CASCADE; CREATE SCHEMA public;"
docker exec -i konfplan_prod pg_restore -U postgres -d konfplan --no-owner /tmp/konfplan.dump
----

`DROP SCHEMA ... CASCADE` statt `pg_restore --clean`, weil `--clean` beim erneuten Restore die neuen, per Migration hinzugekommenen Tabellen (die ja nicht im Dump stehen) nicht kennt und an deren Fremdschlüssel-Abhängigkeiten auf `nutzer`/`veranstaltung` scheitert.

=== 4b. Vollständiger Weg: die App selbst starten, Flyway migriert automatisch

Für einen Klick-Test der betroffenen UI gegen echte Daten (oder um die Migration inklusive korrekter `flyway_schema_history`-Buchführung zu testen) bringt das Repo `db/ensure_prod_infra.sh` mit (startet zusätzlich Keycloak und Mailpit) sowie den passenden Start-Befehl.

[IMPORTANT]
====
Dafür **nicht** `mvnw quarkus:dev` verwenden! Der Dev-Modus nutzt `drop-and-create` für das Schema und würde die wiederhergestellten Daten sofort überschreiben, statt die Flyway-Migration auszuführen.
====

[IMPORTANT]
====
Vor dem Start sicherstellen, dass `backend/target/quarkus-app` **aktuell** ist - ein reines `mvnw test`/`compile` aktualisiert nur `target/classes`, nicht `target/quarkus-app` (das tatsächlich zur Laufzeit verwendete Layout). Im Zweifel neu bauen.

Für einen Login über den Browser zusätzlich `VITE_KEYCLOAK_URL` beim Bauen auf die tatsächliche lokale Keycloak-Adresse setzen (siehe Erklärung unten) - `frontend/src/keycloak.js` baut den Provider-Endpunkt in einem Prod-Build sonst fest auf `window.location.origin + "/auth"` (den Pfad, den nur der reale Caddy-Reverse-Proxy aus `deploy/` bereitstellt), was hier ins Leere läuft:

[source,bash]
----
cd backend && ../mvnw -q package -DskipTests \
  -Dquarkus.quinoa.package-manager-command.build-env.VITE_KEYCLOAK_URL=http://localhost:8080
----

`VITE_KEYCLOAK_URL` ist eine Vite-Build-Zeit-Variable - sie wird beim `npm run build` fest in das JS-Bundle eingebacken und lässt sich danach NICHT mehr per Laufzeit-Umgebungsvariable überschreiben. Ohne diesen Login-Test (z.B. bei einer rein API-basierten Prüfung) kann der Build ohne diesen Parameter erfolgen.
====

Start (Beispielwerte, siehe von `ensure_prod_infra.sh` ausgegebene `export`-Zeilen für die tatsächlichen Ports/Secrets):

[source,bash]
----
DB_HOST=localhost DB_PORT=5432 DB_NAME=konfplan DB_USER=postgres DB_PASSWORD=postgres \
KC_SERVER_URL=http://localhost:8080 KC_REALM=konfplan KC_ADMIN_CLI_SECRET=local-native-test-secret \
QUARKUS_MAILER_HOST=localhost QUARKUS_MAILER_PORT=1025 QUARKUS_MAILER_START_TLS=DISABLED \
QUARKUS_MAILER_USERNAME=test QUARKUS_MAILER_PASSWORD=test \
java -jar backend/target/quarkus-app/quarkus-run.jar
----

Das Log sollte `Migrating schema "public" to version "28 - ..."` und `Successfully applied 1 migration` zeigen. Die App ist danach unter `http://localhost:9000` erreichbar.

== 5. Als echter Nutzer einloggen (ohne Keycloak-Datenbank wiederherzustellen)

`ensure_prod_infra.sh` erzeugt ein frisches, leeres Keycloak-Realm (Bootstrap-Login `admin`/`admin`) - die in der wiederhergestellten `konfplan`-Datenbank stehenden echten Nutzer haben zwar Datensätze, aber (noch) keinen passenden Keycloak-Account in dieser lokalen Instanz, da ihre `keycloak_id`-Spalte auf die *echte* PROD-Keycloak-Instanz verweist, die hier nicht existiert.

Um trotzdem als ein bestimmter, bereits real existierender Nutzer einloggen zu können, ohne dafür `keycloak.dump` wiederherzustellen (siehe Warnhinweis unten für den Vollständigkeits-Fall), reicht es, für genau diesen einen Nutzer lokal einen neuen Keycloak-Account anzulegen und die `keycloak_id` in Postgres darauf umzubiegen:

[source,bash]
----
# 1. Passenden echten Nutzer auswählen
docker exec konfplan_prod psql -U postgres -d konfplan -tAc \
  "select id, login_name, email, role from nutzer where role in ('ORGANISATOR','ADMINISTRATOR') order by role;"

# 2. Admin-Token vom lokalen (frischen) Keycloak holen
TOKEN=$(curl -s -X POST "http://localhost:8080/realms/master/protocol/openid-connect/token" \
  -d "client_id=admin-cli" -d "username=admin" -d "password=admin" -d "grant_type=password" \
  | python3 -c "import sys,json; print(json.load(sys.stdin)['access_token'])")

# 3. Keycloak-User anlegen (loginName/email/Namen aus Schritt 1 einsetzen)
curl -s -i -X POST "http://localhost:8080/admin/realms/konfplan/users" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"username":"<loginName>","email":"<email>","firstName":"<Vorname>","lastName":"<Nachname>","enabled":true,"emailVerified":true}'
# -> Location-Header der Antwort enthält die neue Keycloak-User-Id

# 4. Passwort setzen (nicht-temporär, damit kein Zwangs-Passwortwechsel beim Login kommt)
USER_ID="<neue-keycloak-user-id-aus-schritt-3>"
curl -s -X PUT "http://localhost:8080/admin/realms/konfplan/users/$USER_ID/reset-password" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"type":"password","value":"Konfplan1!","temporary":false}'

# 5. Passende Realm-Rolle zuweisen (ORGANISATOR/ADMINISTRATOR/REFERENT/TEILNEHMER)
ROLE_ID=$(curl -s "http://localhost:8080/admin/realms/konfplan/roles/ADMINISTRATOR" \
  -H "Authorization: Bearer $TOKEN" | python3 -c "import sys,json; print(json.load(sys.stdin)['id'])")
curl -s -X POST "http://localhost:8080/admin/realms/konfplan/users/$USER_ID/role-mappings/realm" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d "[{\"id\":\"$ROLE_ID\",\"name\":\"ADMINISTRATOR\"}]"

# 6. Nutzer-Datensatz in Postgres auf die neue Keycloak-Id verknüpfen
docker exec konfplan_prod psql -U postgres -d konfplan -c \
  "update nutzer set keycloak_id = '$USER_ID' where login_name = '<loginName>';"
----

Danach Login mit `<loginName>` / `Konfplan1!` möglich - mit vollem Zugriff auf die echten, wiederherstellten Daten dieses Nutzers.

[NOTE]
====
Für einen vollständigen Restore der echten Keycloak-Datenbank (alle Nutzer inkl. ihrer echten Passwort-Hashes, keine manuelle Einzelanlage nötig) siehe stattdessen die Restore-Prozedur für `keycloak.dump` - das bringt allerdings zwei Fallstricke mit: der `master`-Realm-Bootstrap-Login (`admin`/`admin`) funktioniert danach nicht mehr (die echten PROD-Master-Credentials wären nötig), und der `admin-cli`-Client-Secret muss nach dem Restore im lokalen Realm neu gesetzt und mit `KC_ADMIN_CLI_SECRET` synchron gehalten werden, da der App-eigene Keycloak-Admin-REST-Client sonst nicht mehr authentifizieren kann.
====

== 6. Aufräumen

[source,bash]
----
docker rm -f konfplan_prod konfplan_prod_keycloak konfplan_prod_mailpit
rm -rf /tmp/konfplan-restore konfplan-backup_*.zip
----

Damit verbleiben keine Kopien der PROD-Daten auf der lokalen Maschine.
