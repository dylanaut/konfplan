== Überblick

=== Ausgangslage

KonfPlan authentifiziert Nutzer aktuell über `quarkus-security-jpa`:

* Passwörter als BCrypt-Hash in `nutzer.password_hash` gespeichert
* JWT-Token werden intern mit RSA-Schlüsselpaar (`privateKey.pem`) erzeugt
* `AuthResource` verwaltet Login, Passwort-Reset und E-Mail-Änderung selbst
* Nutzer werden direkt per Panache in PostgreSQL angelegt (CSV-Import, Admin-UI)

=== Zielarchitektur

[plantuml, target=auth-flow, format=svg]
....
Frontend --> Keycloak : Authorization Code + PKCE
Keycloak --> Frontend : Access Token (JWT)
Frontend --> Backend  : Bearer <token>
Backend  --> Keycloak : JWKS-Verifikation (einmalig gecacht)
....

* Keycloak übernimmt Identitätsmanagement (Login-UI, Token-Ausstellung, Passwort-Reset)
* Backend validiert Token via `quarkus-oidc` gegen Keycloak JWKS
* `@RolesAllowed("ADMIN")` etc. bleiben unverändert
* `AdminService` legt Nutzer künftig via Keycloak Admin REST API an
* Die `Nutzer`-Entität in PostgreSQL bleibt als Domänenobjekt erhalten (Prioritäten, Gruppen, Verfügbarkeiten)

=== Risiken & Grenzen

[NOTE]
====
* BCrypt-Hashes lassen sich nach Keycloak migrieren (Format kompatibel ab Keycloak 21)
* Passwort-Reset-Workflow entfällt im Backend — Keycloak bietet eigene Reset-E-Mails
* E-Mail-Änderungs-Workflow entfällt — Keycloak verwaltet die E-Mail
* `resetToken`, `resetTokenExpiry`, `newEmail`, `emailChangeToken`-Felder aus `Nutzer` können nach Migration via Flyway entfernt werden
====

== Phase 2: Nutzer migrieren

=== Strategie

Keycloak akzeptiert BCrypt-Hashes im `CredentialRepresentation`-Format. Da alle CSV-importierten Nutzer das Standardpasswort `start123` haben, gibt es zwei Optionen:

|===
| Option | Vorteil | Nachteil
| BCrypt-Hash übertragen | Nutzer bemerken nichts | Komplexeres Migrationsskript
| `temporary=true` setzen | Einfach | Alle Nutzer müssen Passwort neu setzen
|===

[RECOMMENDATION]
====
Empfehlung: BCrypt-Hashes migrieren (`start123`-Hash ist bekannt), plus `requiredActions: ["UPDATE_PASSWORD"]` setzen — so können Nutzer ihr Passwort beim nächsten Login ändern, müssen es aber nicht sofort.
====

=== Migrationsskript (Python)

[source,python]
----
#!/usr/bin/env python3
"""
migrate_users_to_keycloak.py
Liest Nutzer aus PostgreSQL und legt sie in Keycloak an.
Voraussetzungen: pip install psycopg2-binary requests
"""

import psycopg2
import requests
import json
import sys

# --- Konfiguration ---
PG_DSN   = "host=localhost port=65432 dbname=konfplan user=postgres password=postgres"
KC_URL   = "http://localhost:8080"
KC_REALM = "konfplan"
KC_ADMIN_USER = "admin"
KC_ADMIN_PASS = "admin"

ROLE_MAP = {"ADMIN": "ADMIN", "REFERENT": "REFERENT", "TEILNEHMER": "TEILNEHMER"}

# --- Keycloak Admin-Token holen ---
def get_admin_token():
    r = requests.post(f"{KC_URL}/realms/master/protocol/openid-connect/token", data={
        "grant_type": "password",
        "client_id": "admin-cli",
        "username": KC_ADMIN_USER,
        "password": KC_ADMIN_PASS,
    })
    r.raise_for_status()
    return r.json()["access_token"]

def headers(token):
    return {"Authorization": f"Bearer {token}", "Content-Type": "application/json"}

# --- Rolle-ID nachschlagen ---
def get_role(token, role_name):
    r = requests.get(f"{KC_URL}/admin/realms/{KC_REALM}/roles/{role_name}", headers=headers(token))
    r.raise_for_status()
    return r.json()

# --- Nutzer anlegen ---
def create_user(token, row):
    user_id, email, first, last, password_hash, role, is_active = row
    kc_user = {
        "username": email,
        "email": email,
        "firstName": first or "",
        "lastName":  last or "",
        "enabled": bool(is_active),
        "emailVerified": True,
        # BCrypt-Hash direkt übertragen
        "credentials": [{
            "type": "password",
            "userLabel": "migrated",
            "temporary": False,
            "secretData": json.dumps({"value": password_hash, "salt": ""}),
            "credentialData": json.dumps({"hashIterations": 10, "algorithm": "bcrypt"}),
        }],
        "requiredActions": ["UPDATE_PASSWORD"],
        "attributes": {
            "db_id": [str(user_id)],
            "konfplan_role": [role],
        }
    }
    r = requests.post(
        f"{KC_URL}/admin/realms/{KC_REALM}/users",
        headers=headers(token),
        json=kc_user,
    )
    if r.status_code == 409:
        print(f"  SKIP (already exists): {email}")
        return None
    r.raise_for_status()
    # Location-Header enthält neue User-ID
    kc_id = r.headers["Location"].rstrip("/").split("/")[-1]
    return kc_id

# --- Realm-Rolle zuweisen ---
def assign_role(token, kc_user_id, role_name):
    role = get_role(token, role_name)
    r = requests.post(
        f"{KC_URL}/admin/realms/{KC_REALM}/users/{kc_user_id}/role-mappings/realm",
        headers=headers(token),
        json=[role],
    )
    r.raise_for_status()

# --- Main ---
def main():
    token = get_admin_token()
    conn  = psycopg2.connect(PG_DSN)
    cur   = conn.cursor()
    cur.execute("""
        SELECT id, email, first_name, last_name, password_hash, dtype, is_active
        FROM nutzer
        ORDER BY id
    """)
    rows = cur.fetchall()
    print(f"Migriere {len(rows)} Nutzer...")

    for row in rows:
        email = row[1]
        role  = row[5]  # DTYPE = Admin, Referent, Teilnehmer
        # dtype → Keycloak-Rollenname
        kc_role = role.upper() if role.upper() in ROLE_MAP else "TEILNEHMER"
        print(f"  {email} [{kc_role}]", end=" ")
        kc_id = create_user(token, row)
        if kc_id:
            assign_role(token, kc_id, kc_role)
            print("OK")

    conn.close()
    print("Fertig.")

if __name__ == "__main__":
    main()
----

=== AuthResource.java (ersetzen)

Der gesamte `AuthResource` wird auf einen minimalen Endpunkt reduziert — Login, Passwort-Reset und E-Mail-Änderung entfallen komplett (Keycloak übernimmt).

Was bleibt: das `/api/auth/me`-Endpunkt, damit das Frontend Nutzer-ID + Rolle aus dem Token lesen kann.

[source,java]
----
@Path("/api/auth")
@ApplicationScoped
public class AuthResource {

    @Inject
    JsonWebToken jwt;                          // <1>

    @GET
    @Path("/me")
    @Authenticated
    @Produces(MediaType.APPLICATION_JSON)
    public Response me() {
        String email = jwt.getClaim("email");
        String sub   = jwt.getSubject();       // Keycloak user-id
        return Response.ok(Map.of(
            "sub",   sub,
            "email", email
        )).build();
    }
}
----
<1> `JsonWebToken` wird von Quarkus OIDC injiziert und enthält alle Claims aus dem Keycloak-Token.

`AuthResource.login()`, `forgotPassword()` und `resetPassword()` entfallen ersatzlos.
Die Endpunkte `/api/auth/login` und `/api/auth/reset-password` werden aus dem Frontend entfernt.

=== AdminService.java (Nutzer-CRUD via Keycloak Admin Client)

Der `AdminService` injiziert den Keycloak Admin Client und ruft alle Identity-Operationen über ihn ab. Die Domänen-Entität in PostgreSQL wird weiterhin per Panache verwaltet.

[source,java]
----
@ApplicationScoped
public class AdminService implements AdminServiceInterface {

    @Inject
    Keycloak keycloak;                                     // <1>

    @Value("${quarkus.keycloak.admin-client.realm}")
    String realm;

    // --- Nutzer anlegen ---
    @Transactional
    @Override
    public NutzerDto createUser(NutzerDto dto, List<Long> veranstaltungsIds) {

        // 1. Keycloak-User anlegen
        UserRepresentation kcUser = new UserRepresentation();
        kcUser.setUsername(dto.email);
        kcUser.setEmail(dto.email);
        kcUser.setFirstName(dto.firstName);
        kcUser.setLastName(dto.lastName);
        kcUser.setEnabled(true);
        kcUser.setEmailVerified(true);

        CredentialRepresentation cred = new CredentialRepresentation();
        cred.setType(CredentialRepresentation.PASSWORD);
        cred.setValue("start123");                          // <2>
        cred.setTemporary(true);
        kcUser.setCredentials(List.of(cred));
        kcUser.setRequiredActions(List.of("UPDATE_PASSWORD"));

        Response resp = keycloak.realm(realm).users().create(kcUser);
        if (resp.getStatus() != 201) {
            throw new WebApplicationException("Keycloak: Nutzer konnte nicht angelegt werden", 500);
        }
        String kcId = resp.getLocation().getPath().replaceAll(".*/([^/]+)$", "$1");

        // 2. Realm-Rolle zuweisen
        RoleRepresentation role = keycloak.realm(realm).roles()
            .get(dto.role).toRepresentation();
        keycloak.realm(realm).users().get(kcId)
            .roles().realmLevel().add(List.of(role));

        // 3. Domänen-Entität in PostgreSQL anlegen
        Nutzer nutzer = buildNutzerEntity(dto);             // <3>
        nutzer.persistAndFlush();

        // 4. Veranstaltungen zuweisen
        assignVeranstaltungen(nutzer, veranstaltungsIds);

        return NutzerDto.from(nutzer);
    }

    // --- Nutzer löschen ---
    @Transactional
    @Override
    public void deleteUser(Long id) {
        Nutzer nutzer = Nutzer.findById(id);
        if (nutzer == null) throw new WebApplicationException(404);

        // Keycloak-User per E-Mail suchen und löschen
        List<UserRepresentation> results = keycloak.realm(realm).users()
            .searchByEmail(nutzer.email, true);
        if (!results.isEmpty()) {
            keycloak.realm(realm).users().delete(results.getFirst().getId());
        }

        nutzer.delete();
    }

    // ... updateUser analog
}
----
<1> `io.quarkus.keycloak.admin.client.runtime.Keycloak` wird von `quarkus-keycloak-admin-rest-client` bereitgestellt.
<2> Temporäres Passwort — Nutzer muss es beim ersten Login ändern.
<3> Kein `passwordHash` mehr — der Nutzer enthält nur noch Domänendaten.
