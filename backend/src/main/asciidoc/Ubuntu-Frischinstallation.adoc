== Überblick

Dieses Dokument fasst zwei vollständige Installationswege für eine *frische Ubuntu-Maschine*
(getestet gegen Ubuntu 24.04 LTS Server) zusammen und ergänzt sie um den Weg, die Anwendung
direkt aus dem Quellcode zu bauen und ihre automatisierten Tests laufen zu lassen.
Beide Deployment-Wege existieren unabhängig voneinander im Repo und werden an anderer Stelle
bereits im Detail beschrieben - dieses Dokument dient als kompakter Einstiegspunkt, der beide
nebeneinanderstellt:

[cols="1,3,3", options="header"]
|===
| Weg | Vorteil | Ausführliche Doku
| Docker Compose | Isoliert (App/DB/Keycloak je eigener Container), einfaches Backup/Umzug, identisch nutzbar lokal (UTM) und auf Hetzner Cloud | `Deployment-DockerCompose.adoc`
| `.deb`-Pakete (systemd) | Näher an einer klassischen Server-Installation (PostgreSQL nativ statt Container), `apt`-verwaltet | `packaging/debian/README.md`, `install.sh`
|===

Für beide Wege gilt: Passwörter/Secrets landen **nie** im Repository - sie werden beim jeweiligen
Setup automatisch generiert bzw. in `.env`-/`*.env`-Dateien außerhalb des Repos gepflegt.

== Gemeinsame Voraussetzungen

Auf der frischen Ubuntu-Maschine zunächst installieren:

[source,bash]
----
sudo apt-get update
sudo apt-get install -y git curl openssl openjdk-21-jdk nodejs npm

# Docker: NICHT das docker.io-Paket aus den Ubuntu-Repos (Compose-Plugin fehlt dort),
# sondern das offizielle Docker-Repo - wird für beide Wege gebraucht
# (Weg A direkt, Weg B für Keycloak/Mailpit-Container):
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker $USER
newgrp docker   # oder ab-/anmelden, damit die Gruppenzugehörigkeit greift
docker compose version   # sollte funktionieren
----

MiniZinc (Constraint-Solver für die PlanErstellung, sowohl zur Laufzeit als auch für Backend-Tests
nötig):

[source,bash]
----
sudo apt-get install -y minizinc || true
minizinc --version
----

Falls das Paket in den Ubuntu-Repos fehlt oder zu alt ist, alternativ das Release-Bundle laden
(wie in der CI, `.github/workflows/ci.yml`):

[source,bash]
----
ASSET_URL=$(curl -fsSL https://api.github.com/repos/MiniZinc/MiniZincIDE/releases/latest \
  | grep -o '"browser_download_url": *"[^"]*bundle-linux-x86_64\.tgz"' | head -1 | cut -d'"' -f4)
curl -fsSL -o /tmp/minizinc.tgz "$ASSET_URL"
mkdir -p "$HOME/minizinc" && tar -xzf /tmp/minizinc.tgz -C "$HOME/minizinc" --strip-components=1
"$HOME/minizinc/bin/minizinc" --version
export MINIZINC_PATH="$HOME/minizinc/bin/minizinc"   # überschreibt minizinc.path in application.properties
----

=== Repository klonen (privates Repo, `gh` CLI + PAT)

`https://github.com/dylanaut/konfplan` ist ein **privates** Repository. Ein einfaches
`git clone https://github.com/...` scheitert auf einer frischen Maschine mit
`Password authentication is not supported` - GitHub akzeptiert seit 2021 über HTTPS nur noch
einen *Personal Access Token* (PAT) oder SSH, kein Account-Passwort mehr. Der einfachste Weg auf
einer frischen VM ist die `gh`-CLI, die den PAT einmalig hinterlegt und danach auch normales
`git clone`/`git pull`/`git push` transparent authentifiziert.

==== `gh` CLI installieren

Offizielles APT-Repo (funktioniert identisch auf Debian und Ubuntu, siehe
https://github.com/cli/cli/blob/trunk/docs/install_linux.md):

[source,bash]
----
(type -p wget >/dev/null || sudo apt-get install wget -y)
sudo mkdir -p -m 755 /etc/apt/keyrings
out=$(mktemp) && wget -nv -O "$out" https://cli.github.com/packages/githubcli-archive-keyring.gpg
sudo cp "$out" /etc/apt/keyrings/githubcli-archive-keyring.gpg
sudo chmod go+r /etc/apt/keyrings/githubcli-archive-keyring.gpg
sudo mkdir -p -m 755 /etc/apt/sources.list.d
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/githubcli-archive-keyring.gpg] https://cli.github.com/packages stable main" \
  | sudo tee /etc/apt/sources.list.d/github-cli.list > /dev/null
sudo apt-get update
sudo apt-get install -y gh
----

==== Personal Access Token (PAT) erzeugen

Auf github.com: *Settings → Developer settings → Personal access tokens* (fine-grained oder
classic) → neues Token mit Lesezugriff (`repo`-Scope bei classic bzw. *Contents: Read* bei
fine-grained) auf `dylanaut/konfplan` erzeugen. Token direkt nach Erzeugung kopieren - er wird von
GitHub nur einmal angezeigt.

==== `gh` authentifizieren und Git dafür einrichten

[source,bash]
----
# Interaktiv (Browser/Terminal auf derselben Maschine verfuegbar):
gh auth login
# -> "GitHub.com" -> "HTTPS" -> "Paste an authentication token" -> Token einfuegen

# Alternative fuer eine headless VM ohne Browser (Token vorher z.B. per Password-Manager-CLI
# oder einer chmod-600-Datei bereitstellen, NICHT direkt in der Shell-History belassen):
gh auth login --with-token < token.txt

# Prüfen:
gh auth status

# Git selbst (nicht nur "gh repo clone") auf den gh-Credential-Helper umstellen, damit auch
# "git clone/pull/push" mit https://github.com/... ohne weitere Eingabe funktionieren:
gh auth setup-git
----

==== Klonen

[source,bash]
----
gh repo clone dylanaut/konfplan
# aequivalent, sobald "gh auth setup-git" gelaufen ist, auch:
# git clone https://github.com/dylanaut/konfplan.git
cd konfplan
----

== Weg A: Docker Compose

Alle Komponenten (App, PostgreSQL, Keycloak, optional Mailpit) laufen als Container, gesteuert über
`deploy/docker-compose.yml`. Details/Troubleshooting/Hetzner-Profil `public` (TLS via Caddy) siehe
`Deployment-DockerCompose.adoc` - hier nur der lokale/lokal-öffentliche Standardfall (Profil ohne
`--profile`, entspricht dem UTM-Fall).

=== Vorab: Docker-Login bei `ghcr.io`

Das `app`-Image (`ghcr.io/dylanaut/konfplan:latest`) ist - wie das Repository selbst - **privat**.
Ein `docker compose up` ohne vorherigen Login schlägt mit `unauthorized` fehl (die anderen
Images wie `keycloak`/`mailpit` werden dabei ebenfalls abgebrochen, da Compose bei einem
Pull-Fehler alle parallelen Pulls stoppt). Mit einem PAT mit Scope `read:packages` einloggen
(derselbe PAT wie für `gh`/`git` funktioniert, sofern er diesen Scope hat, sonst zusätzlichen PAT
erzeugen):

[source,bash]
----
echo "<dein-PAT>" | docker login ghcr.io -u <dein-github-username> --password-stdin
----

[source,bash]
----
cd deploy
cp .env.example .env        # Standardwerte reichen lokal unveraendert
./bootstrap.sh              # generiert DB-/Keycloak-Passwoerter in secrets/*.txt (idempotent)
docker compose up -d        # startet App + Postgres + Keycloak (+ optional Mailpit)
----

Danach:

* *App*: `http://localhost:9000`
* *Keycloak-Admin-Konsole*: `http://localhost:8080` - Login `admin` / Inhalt von
  `deploy/secrets/keycloak_admin_password.txt`
* Status/Logs: `docker compose ps`, `docker compose logs -f app`

=== Erster Login-Account

Der DB-seitige Bootstrap-Admin (`juergenkrey`, aus `V2__data.sql`) existiert nur als Datenbankzeile,
nicht in Keycloak. Er muss **einmalig manuell** über die Keycloak-Admin-Konsole angelegt werden:
Login-Name muss exakt `juergenkrey` lauten, Rolle `ADMIN` zuweisen. Erst danach ist ein Login in der
App als Admin möglich.

Das geht statt per Web-UI auch komplett per Kommandozeile über das in Keycloak eingebaute
`kcadm.sh`:

[source,bash]
----
cd deploy

# 1. kcadm gegen den lokalen Keycloak mit dem Admin-Account authentifizieren
docker compose exec keycloak /opt/keycloak/bin/kcadm.sh config credentials \
  --server http://localhost:8080 --realm master --user admin \
  --password "$(cat secrets/keycloak_admin_password.txt)"

# 2. Nutzer im "konfplan"-Realm anlegen - Login-Name MUSS exakt "juergenkrey" sein
docker compose exec keycloak /opt/keycloak/bin/kcadm.sh create users -r konfplan \
  -s username=juergenkrey \
  -s email=juergenkrey@yahoo.de \
  -s enabled=true \
  -s emailVerified=true

# 3. Passwort setzen (das eigentliche Login-Passwort - nicht der Hash aus V2__data.sql!)
docker compose exec keycloak /opt/keycloak/bin/kcadm.sh set-password -r konfplan \
  --username juergenkrey --new-password "<dein-passwort>" --temporary=false

# 4. Realm-Rolle ADMIN zuweisen
docker compose exec keycloak /opt/keycloak/bin/kcadm.sh add-roles -r konfplan \
  --uusername juergenkrey --rolename ADMIN
----

Das Passwort aus Schritt 3 ist das künftige Login-Passwort für die App - der `password_hash` in
`V2__data.sql` ist irrelevant, da Zugangsdaten ausschließlich in Keycloak liegen (siehe CLAUDE.md:
"Identity/passwords live in Keycloak, not in the database"). Die DB-Zeile dient nur dazu, den
Login-Namen `juergenkrey` beim ersten Login mit dem bestehenden `ADMIN`-Datensatz zu verknüpfen.

=== Troubleshooting: `docker.io` nicht erreichbar (Corporate-Netz)

In manchen Firmennetzen (z.B. mit TLS-Interception/Proxy-Zwang für ausgehenden Traffic) scheitert
der Pull einzelner Images mit einer Meldung wie:

[source]
----
failed to resolve reference "docker.io/axllent/mailpit:latest": failed to do request:
Head "https://registry-1.docker.io/v2/...": dial tcp ...: connect: connection refused
----

Das ist kein KonfPlan-/Compose-Problem, sondern eine Netzwerk-Restriktion des Hosts: Der Docker-
Daemon kommt nicht direkt zu Docker Hub raus (andere Registries wie `ghcr.io` können davon
unabhängig funktionieren oder ebenfalls betroffen sein). Docker Compose bricht dabei alle
parallelen Image-Pulls ab, sobald einer fehlschlägt - die übrigen Images erscheinen dann nur als
"Interrupted", nicht als eigentlicher Fehler.

**Wichtig, bevor man einen generischen Unternehmens-Proxy sucht:** In Netzen, in denen bereits ein
interner npm-Mirror für `registry.npmjs.org` genutzt wird (siehe `frontend/.npmrc`), lief bei
diesem Fehlerbild kein klassischer System-/Shell-Proxy (`HTTP_PROXY`/`HTTPS_PROXY`) - weder
`scutil --proxy` (macOS) noch die Shell-Umgebung, `git`- oder `npm`-Konfiguration zeigten einen
konfigurierten Proxy. Das Muster ist eher gezieltes Blocken/Umleiten einzelner öffentlicher
Registries als ein genereller Forward-Proxy für allen Traffic. Deshalb zuerst dort prüfen, wo das
tatsächliche Problem auftritt (auf der betroffenen VM selbst, nicht auf dem Host-Rechner):

[source,bash]
----
env | grep -i proxy
cat /etc/environment
cat /etc/apt/apt.conf.d/*proxy* 2>/dev/null   # falls apt bereits ueber einen Proxy laeuft, Docker aber nicht
----

Abhilfe, je nachdem was zutrifft (im Zweifel IT/Netzwerk-Team fragen):

* **Registry-Mirror** (naheliegender, falls das Nexus-Muster wie beim npm-Mirror zutrifft): falls
  im selben internen Nexus/Artifactory zusätzlich ein Docker/OCI-Proxy-Repository existiert, dessen
  URL in `/etc/docker/daemon.json` unter `"registry-mirrors": ["<interne-mirror-url>"]` eintragen
  und Docker neu starten.
* **Proxy** (nur falls tatsächlich einer existiert, z.B. auf der VM selbst gefunden): Docker-Daemon
  darauf verweisen, z.B. via `/etc/systemd/system/docker.service.d/http-proxy.conf`
  (`HTTP_PROXY`/`HTTPS_PROXY`/`NO_PROXY`), danach
  `sudo systemctl daemon-reload && sudo systemctl restart docker`.

=== Von lokal zu öffentlich (Profil `public`)

Das oben beschriebene Standard-Setup bindet die App per `APP_PORT_BINDING=127.0.0.1:9000:9000`
nur an `localhost` - von außen (auch nicht aus dem gleichen LAN) nicht erreichbar. Für einen
**dauerhaft öffentlich erreichbaren** Betrieb (echte Domain + automatisches TLS) auf das Profil
`public` umsteigen (Details siehe `Deployment-DockerCompose.adoc`, Abschnitt "Hetzner Cloud").

**Wichtig, falls bereits mit lokalem Profil gestartet wurde:** `--import-realm` importiert das
Keycloak-Realm nur beim allerersten Start. Ein Client, der bereits mit
`APP_PUBLIC_URL=http://localhost:9000` importiert wurde, bekommt die neue Domain nicht automatisch
nachgetragen. Solange noch keine echten Nutzdaten existieren, ist ein sauberer Neustart mit den
richtigen Werten von Anfang an einfacher als nachträgliches Editieren der Redirect-URIs in der
Keycloak-Admin-Konsole.

. **DNS**: zwei A-Records auf die öffentliche Server-IP (App und Keycloak brauchen getrennte
Hostnamen):
+
--
.. Öffentliche IP des Servers ermitteln:
+
[source,bash]
----
curl -4 ifconfig.me
----
(alternativ aus der Cloud-Provider-Konsole ablesen, z.B. Hetzner Cloud Console am Server).

.. Ins DNS-Management der Domain einloggen - dort, wo die Domain registriert/verwaltet wird, z.B.
**Hetzner DNS Console** (`dns.hetzner.com`, passt gut zu Hetzner Cloud) oder die
Konsole des jeweiligen Registrars/DNS-Anbieters (Cloudflare, IONOS/1&1, Namecheap, GoDaddy, ...) -
Bereich meist "DNS" oder "Nameserver-Einstellungen" genannt. Ohne eigene, selbst verwaltete Domain
funktioniert das Profil `public` mit echtem TLS nicht - die Domain muss vorher bei einem Registrar
erworben werden.

.. Zwei A-Records anlegen (Feldnamen variieren je Anbieter, meist "Name"/"Host" und
"Wert"/"Ziel"/"Points to"):
+
[cols="1,2,2", options="header"]
|===
| Typ | Name/Host | Wert
| A | `konfplan` (bzw. `konfplan.<sub>`) | `<server-ip>`
| A | `auth.konfplan` | `<server-ip>`
|===

.. Propagation prüfen, bevor `bootstrap.sh public`/`docker compose --profile public up -d`
gestartet wird - sonst scheitert Caddys automatischer Let's-Encrypt-Bezug:
+
[source,bash]
----
dig +short konfplan.<deine-domain>
dig +short auth.konfplan.<deine-domain>
----
Beide sollten `<server-ip>` liefern.
--

. **Firewall**: nur SSH (den tatsächlich genutzten Port, ggf. abweichend von 22), HTTP (80) und
HTTPS (443) von außen erlauben - Postgres/Keycloak/App-Ports NICHT. Das betrifft die OS-Firewall
auf der VM selbst (`ufw`), zusätzlich zu einer eventuell vorgeschalteten Cloud-Firewall (siehe
unten):
+
[source,bash]
----
# Status pruefen (zeigt, ob ufw ueberhaupt aktiv/installiert ist)
sudo ufw status verbose

# falls nicht installiert:
sudo apt-get install -y ufw
----
+
[IMPORTANT]
====
Unbedingt zuerst den tatsächlich genutzten SSH-Port erlauben, bevor `ufw enable` läuft - sonst
sperrt man sich selbst aus der VM aus (Wiederherstellung dann meist nur über die
Cloud-Provider-Konsole möglich).
====
+
[source,bash]
----
sudo ufw allow <ssh-port>/tcp
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable
----
+
Danach prüfen, dass 80/tcp und 443/tcp als `ALLOW` gelistet sind:
+
[source,bash]
----
sudo ufw status numbered
----
+
Läuft der Server bei einem Cloud-Provider (z.B. Hetzner Cloud), zusätzlich prüfen, ob dort
**zusätzlich** eine Cloud-Firewall vorgeschaltet ist - die muss unabhängig von `ufw` ebenfalls Port
80/443 durchlassen, sonst bleibt es trotz `ufw allow` von außen blockiert.

. **`.env` umstellen** (nur unschädlich, falls noch keine echten Daten drin sind - siehe Hinweis
oben):
+
[source,bash]
----
cd deploy
docker compose down -v
----
+
In `.env` ergänzen/anpassen:
+
[source]
----
APP_HOSTNAME=konfplan.<deine-domain>
KEYCLOAK_HOSTNAME=auth.konfplan.<deine-domain>
APP_PUBLIC_URL=https://konfplan.<deine-domain>
ACME_EMAIL=<deine-email>
----
+
Mailversand: entweder `BREVO_SMTP_USER=<dein-brevo-login>` (echter Versand) setzen oder weiterhin
Profil `mailpit` zusätzlich nutzen (Testpostfach, dann aber ebenfalls nicht öffentlich exponieren).

. **Starten**:
+
[source,bash]
----
./bootstrap.sh public
docker compose --profile public up -d
# optional zusaetzlich Mailpit statt echtem SMTP:
docker compose --profile public --profile mailpit up -d
----
+
Caddy bezieht beim ersten Start automatisch Let's-Encrypt-Zertifikate für beide Domains
(`docker compose logs caddy -f` zum Verfolgen). App/Keycloak sind danach nicht mehr direkt per Port,
nur noch über Caddy (80/443) erreichbar.

. **Smoke-Test**:
+
[source,bash]
----
curl -sI https://konfplan.<deine-domain>/
curl -s https://auth.konfplan.<deine-domain>/realms/konfplan/.well-known/openid-configuration | jq .issuer
----

Bootstrap-Admin-Account (`juergenkrey`) danach wie gehabt einmalig manuell in der
Keycloak-Admin-Konsole anlegen.

=== Port 80/443 ohne `ufw` freigeben

Falls kein lokales `ufw` genutzt werden soll (z.B. weil ausschließlich über eine Cloud-Firewall
gefiltert wird), gibt es zwei Alternativen:

* **Direkt per `iptables`**:
+
[source,bash]
----
sudo iptables -I INPUT -p tcp --dport 80 -j ACCEPT
sudo iptables -I INPUT -p tcp --dport 443 -j ACCEPT
----
+
Gilt nur bis zum nächsten Neustart, sofern nicht persistiert:
`sudo apt-get install -y iptables-persistent && sudo netfilter-persistent save`.

* **Nur über die Cloud-Firewall** (z.B. Hetzner Cloud Console → *Firewalls*, oder per CLI):
+
[source,bash]
----
hcloud firewall create --name konfplan-fw
hcloud firewall add-rule konfplan-fw --direction in --protocol tcp --port 80 --source-ips 0.0.0.0/0,::/0
hcloud firewall add-rule konfplan-fw --direction in --protocol tcp --port 443 --source-ips 0.0.0.0/0,::/0
hcloud firewall apply-to-resource konfplan-fw --type server --server <server-name>
----
+
Bei anderen Providern analog über deren Konsole/CLI (AWS Security Group, etc.).

Vor dem Umstieg erst prüfen, was auf der VM überhaupt aktiv ist:
[source,bash]
----
sudo ufw status
sudo iptables -L -n --line-numbers
sudo nft list ruleset 2>/dev/null
----
Ubuntu nutzt standardmäßig `nftables` als Kernel-Backend, `ufw` ist nur ein Frontend dafür - ohne
`ufw` kann trotzdem eine andere Regel blockieren, oder lokal blockiert gar nichts und der
eigentliche Filter sitzt ausschließlich in der Cloud-Firewall.

=== `ufw` wieder entfernen

[source,bash]
----
sudo ufw disable                # zuerst deaktivieren, bevor irgendetwas entfernt wird
sudo systemctl stop ufw
sudo systemctl disable ufw
sudo apt-get purge -y ufw
----

**Falls danach noch `ufw`-Chains in `iptables`/`nftables` sichtbar sind** (z.B. `ufw-before-input`,
`ufw-after-input`, ...): Der zuverlässigste Weg ist `ufw`s eigener Reset, *bevor* das Paket entfernt
wird - der räumt gezielt nur die von `ufw` angelegten Chains auf, ohne Dockers eigene Chains
(`DOCKER`, `DOCKER-USER`, `DOCKER-ISOLATION-STAGE-1/2`) anzufassen, die für die laufenden
KonfPlan-Container gebraucht werden:

[source,bash]
----
sudo apt-get install -y ufw     # falls schon entfernt, kurz erneut installieren
sudo ufw reset                  # fragt Bestaetigung (y), entfernt alle ufw-Chains/-Regeln sauber
sudo systemctl stop ufw
sudo systemctl disable ufw
sudo apt-get purge -y ufw
----

Kontrolle, dass nichts mehr übrig ist:
[source,bash]
----
sudo iptables -L -n | grep -i ufw
sudo ip6tables -L -n | grep -i ufw
----

[IMPORTANT]
====
Nicht `iptables -F`/`-X` (alles flushen) als Abkürzung nutzen - das entfernt auch Dockers eigene
Chains, wodurch die laufenden Container bis zu einem `sudo systemctl restart docker` (das seine
Chains neu anlegt) falsch geroutet/unerreichbar werden können. Falls doch ein harter Reset gemacht
wird, direkt danach `sudo systemctl restart docker` ausführen.

Außerdem: Ohne `ufw` (und ohne eigene `iptables`/`nftables`-Regeln) ist die VM lokal offen für
eingehenden Traffic auf allen Ports - sicherstellen, dass die Cloud-Firewall bereits die
gewünschten Regeln (nur SSH-Port, 80, 443) hat, *bevor* `ufw` entfernt wird.
====

== Weg B: .deb-Pakete (systemd)

Vier eigenständige `.deb`-Pakete (App, PostgreSQL-Setup, Keycloak-Container, Mailpit-Container),
siehe `packaging/debian/README.md`. `install.sh` im Repo-Root automatisiert Bauen + Installieren in
einem Rutsch.

=== Ein-Kommando-Variante

[source,bash]
----
./install.sh
----

Baut Backend+Frontend, erzeugt und installiert alle vier `.deb`-Pakete und öffnet ggf. Port 9000 in

automatisch.

[source,bash]
----
# 1. Backend + Frontend bauen
cd backend && ../mvnw clean package -DskipTests && cd ..

=== Konfiguration vor dem ersten Start

Reihenfolge beachten (`konfplan-keycloak.service` braucht `konfplan-postgresql.service`,
`konfplan.service` braucht eine erreichbare Keycloak-Instanz):

[source,bash]
----
sudo nano /etc/konfplan/postgresql.env  # DB_PASSWORD setzen
sudo systemctl start konfplan-postgresql.service

sudo nano /etc/konfplan/keycloak.env    # DB_PASSWORD (= postgresql.env), KC_ADMIN_PASSWORD,
                                         # KC_ADMIN_CLI_SECRET, KC_HOSTNAME, APP_PUBLIC_URL
sudo systemctl start konfplan-keycloak.service

sudo nano /etc/konfplan/mailpit.env     # optional, Standardwerte meist ok
sudo systemctl start konfplan-mailpit.service

sudo nano /etc/konfplan/konfplan.env    # DB_PASSWORD (= postgresql.env),
                                         # KC_ADMIN_CLI_SECRET (= keycloak.env),
                                         # BREVO_SMTP_* oder Mailpit-Variablen
sudo systemctl start konfplan.service
----

`DB_NAME`/`DB_USER` müssen in `konfplan.env` und `postgresql.env` übereinstimmen (Standard:
`konfplan` in beiden). `KC_ADMIN_CLI_SECRET` muss in `konfplan.env` und `keycloak.env` identisch
sein. Ebenso `KC_SERVER_URL`/`KC_HOSTNAME`+`KEYCLOAK_PORT` und `FRONTEND_BASE_URL`/`APP_PUBLIC_URL`.

Die App ist danach unter `http://<server>:9000` erreichbar. Der Bootstrap-Admin-Account
(`juergenkrey`) muss - genau wie bei Weg A - einmalig manuell in der Keycloak-Admin-Konsole angelegt
werden.

=== Troubleshooting (Auszug)

* **`konfplan-postgresql.service` schlägt fehl**: `systemctl status postgresql` prüfen - das
  Oneshot-Skript nutzt lokale Peer-Authentifizierung, funktioniert nur auf demselben Host.
* **Keycloak-Login funktioniert nicht**: prüfen, ob `keycloak`-Datenbank existiert
  (`konfplan-postgresql.service` muss vorher gelaufen sein) und ob `KC_ADMIN_CLI_SECRET` in beiden
  `.env`-Dateien identisch ist.
* **Firewall**: nur `9000/tcp` (App) und ggf. `8025/tcp` (Mailpit-UI) öffnen. Port 5432
  (PostgreSQL), 8080 (Keycloak), 1025 (Mailpit-SMTP) NICHT nach außen öffnen.
* **Deinstallation**: `sudo apt-get remove konfplan konfplan-postgresql konfplan-keycloak
  konfplan-mailpit` (behält Konfiguration); `apt-get purge` entfernt zusätzlich Konfiguration und
  Systembenutzer, lässt aber die PostgreSQL-Datenbanken/-Rolle als Sicherheitsnetz bestehen.

Vollständige Details siehe `packaging/debian/README.md`.

== Aus dem Quellcode bauen und automatisierte Tests laufen lassen

Unabhängig vom gewählten Deployment-Weg lässt sich die Anwendung auf derselben Maschine auch direkt

=== Backend-Tests

Nutzen H2 in-memory, brauchen aber MiniZinc auf `PATH`/`MINIZINC_PATH` (siehe oben):

[source,bash]
----
./mvnw clean install -DskipTests      # baut Backend + Frontend (Quinoa ruft npm auf)
cd backend && ../mvnw test            # alle Backend-Tests
# einzelne Klasse/Methode:
../mvnw test -Dtest=AdminServiceTest
../mvnw test -Dtest=AdminServiceTest#methodName
----

=== Frontend-E2E-Tests (Playwright)

Siehe `frontend/docs/Playwright.adoc`. Braucht eine laufende App im **Dev-Modus** (nicht die
Docker-Compose- oder `.deb`-Instanz aus den Wegen A/B - dort fehlen die Dev-Testdaten):

[source,bash]
----
# Terminal 1: Backend im Dev-Modus (startet Dev Services fuer Postgres+Keycloak, braucht Docker)
cd backend && ../mvnw quarkus:dev

# Terminal 2: Playwright
cd frontend
npm install
npx playwright install --with-deps
npx playwright test
----
