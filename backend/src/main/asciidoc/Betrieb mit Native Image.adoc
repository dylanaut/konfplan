= KonfPlan: Produktions-Workflow mit Native Image
:toc: left
:icons: font
:source-highlighter: highlightjs

Dieses Dokument beschreibt den Build-Prozess und den Betrieb der KonfPlan Anwendung als **natives Executable** mittels GraalVM.

== 1. Warum Native Image?

Im Vergleich zum Standard-JRE-Modus bietet das Native Image:

* **Startzeit:** < 0.1 Sekunden.
* **Speicherverbrauch:** Deutlich reduzierter RAM-Footprint.
* **Portabilität:** Keine Java-Laufzeitumgebung (JRE) auf dem Zielsystem erforderlich.

== 2. Erstellung des Native Images

Der Build-Prozess integriert über Quinoa automatisch das Frontend und kompiliert anschließend das gesamte Backend nativ.

[IMPORTANT]
====
In `application.properties` ist `%prod.quarkus.native.container-build=true` gesetzt. Das `%prod`-Profil ist bei jedem regulären `package`-Build aktiv, d.h. **der Container-Build wird standardmäßig immer erzwungen** – unabhängig davon, was `JAVA_HOME` sagt oder ob `-Dquarkus.native.container-build` explizit angegeben wird.
====

=== Vorbereitung für andere Plattformen, z.B. debian

[source,bash]
----
sudo apt update && sudo apt install -y curl zip unzip
curl -s "https://get.sdkman.io" | bash
source "$HOME/.sdkman/bin/sdkman-init.sh"
----




=== Variante A: Build mit lokalem GraalVM
Voraussetzung ist ein für dein Host-Betriebssystem/-Architektur passendes GraalVM bzw. Mandrel (z.B. via SDKMAN installiert, `JAVA_HOME` entsprechend gesetzt). Da die Konfiguration den Container-Build erzwingt (siehe oben), muss dieser hier explizit deaktiviert werden:

[source,bash]
----
export JAVA_HOME=<Pfad-zu-GraalVM/Mandrel-für-dein-Host-OS>
# z.B. /Users/kreyj/.sdkman/candidates/java/25.0.2.r25-mandrel
./mvnw clean package -Dnative -DskipTests -Dquarkus.native.container-build=false
----

Das Ergebnis ist ein natives Executable für **dein Host-Betriebssystem** (z.B. macOS/aarch64 auf Apple Silicon), lauffähig direkt auf dem Host ohne Docker.

=== Variante B: Build via Docker/Podman (Standard/Empfohlen)
Ohne weitere Angaben (siehe IMPORTANT oben) baut Quarkus ohnehin in einem Container:

[source,bash]
----
./mvnw clean package -Dnative -DskipTests
----

NOTE: Da das Frontend via Quinoa gebaut wird, müssen **Node.js** und **npm** trotzdem auf dem Host-System vorhanden sein.

[IMPORTANT]
====
Der Container-Build läuft im konfigurierten `builder-image` (ein Linux/UBI-Image). Das erzeugte Executable ist daher immer ein **Linux-Binary** für die Architektur des Docker-Hosts (z.B. `linux/aarch64` auf Apple Silicon mit Docker Desktop) – **kein natives macOS-Binary**. Es ist direkt auf dem Mac nicht ausführbar, sondern nur in einem passenden Linux-Container bzw. auf einem Linux-Host der gleichen Architektur (siehe Abschnitt 6/7).
====

== 3. Starten der Anwendung

Nach dem Build findest du im Verzeichnis `backend/target/` kein JAR-File, sondern eine ausführbare Datei (erkennbar am Suffix `-runner`).

=== Ausführung
[source,bash]
----
./backend/target/konfplan-backend-1.0.0-SNAPSHOT-runner
----

* Die Anwendung ist sofort unter `http://localhost:9000` erreichbar.
* Das Frontend ist bereits in die Binärdatei eingebettet.

[IMPORTANT]
====
Im Native Mode gibt es keine DevServices mehr. PostgreSQL, Keycloak (Authentifizierung) und ein SMTP-Server müssen daher **vor** dem Start des Runners selbst bereitgestellt werden. Dafür gibt es das Hilfsscript:

[source,bash]
----
./db/ensure_prod_infra.sh
----

Es startet idempotent (per Docker-Label wiedererkennbar) einen `postgres:18`-, einen `quay.io/keycloak/keycloak`- und einen `axllent/mailpit`-Container (lokaler Ersatz für den echten Brevo-SMTP-Server aus Abschnitt 4) und gibt am Ende den passenden `export`-Block für den Runner-Start aus.

Der Keycloak-Realm-Import wird dabei aus derselben zentralen Vorlage (`deploy/keycloak-realm.template.json`) gerendert, die auch das Docker-Compose- und das `.deb`-Verfahren nutzen - `konfplan-frontend`/`konfplan-backend`/`konfplan-admin-cli`-Clients und die Rollen `ORGANISATOR`/`ADMINISTRATOR`/`REFERENT`/`TEILNEHMER` sind danach identisch zu den anderen Betriebsarten vorhanden. Ohne laufenden Keycloak startet die Anwendung nicht (OIDC-Verbindungsaufbau schlägt fehl).

Belegt Port 8080 bereits einen anderen lokalen Dienst, kann der Keycloak-Port des Skripts per Umgebungsvariable verschoben werden: `KEYCLOAK_PORT=8180 ./db/ensure_prod_infra.sh`.
====

== 4. Konfiguration im Native Mode

Da im Native Mode die `application.properties` fest in das Binary kompilliert werden, solltest du dynamische Werte (wie Datenbank-URLs oder Passwörter) über **Umgebungsvariablen** übergeben:

[source,bash]
----
export QUARKUS_DATASOURCE_JDBC_URL=jdbc:postgresql://prod-db:5432/konfplan
export QUARKUS_DATASOURCE_USERNAME=admin
export QUARKUS_DATASOURCE_PASSWORD=geheim
export KC_SERVER_URL=http://localhost:8080
export KC_REALM=konfplan
export KC_ADMIN_CLI_SECRET=geheim
export TEMPLATES_DIR=/opt/konfplan/templates
./backend/target/konfplan-backend-1.0.0-SNAPSHOT-runner
----

`KC_SERVER_URL`/`KC_REALM` müssen auf einen erreichbaren Keycloak-Realm zeigen (siehe Abschnitt 3), `KC_ADMIN_CLI_SECRET` auf das Client-Secret des `konfplan-admin-cli`-Clients in genau diesem Realm - andernfalls schlagen alle Nutzerverwaltungs-Aufrufe (Anlegen/Ändern/Löschen, Passwort-Reset) fehl, da `KeycloakUserProvisioningService` sich damit gegen die Keycloak Admin REST API authentifiziert.

Für den echten Produktivbetrieb kommen zusätzlich die Zugangsdaten des Mailservers dazu (`BREVO_SMTP_USER`/`BREVO_SMTP_PASSWORD`, siehe `%prod.quarkus.mailer.username`/`.password` in `application.properties`).

[IMPORTANT]
====
Diese Zugangsdaten dürfen **nicht** im Git-Repository landen (auch nicht in `application.properties` selbst – dort steht nur der Verweis `${BREVO_SMTP_USER}`). Zwei gängige Wege, sie trotzdem bereitzustellen:

* **CI/CD-Pipeline (GitLab):** Als *maskierte* + *geschützte* CI/CD-Variablen unter *Project → Settings → CI/CD → Variables* anlegen. Der `deploy_to_production`-Job in `.gitlab-ci.yml` reicht sie dann per `-e BREVO_SMTP_USER=${BREVO_SMTP_USER}` an den entfernten `docker run`-Aufruf durch.
* **Direkt auf dem Server** (z.B. bei diesem manuellen Runner-Start): eine Datei außerhalb des Repos anlegen, z.B. `/etc/konfplan/prod.env` mit `chmod 600`:
+
[source,bash]
----
BREVO_SMTP_USER=...
BREVO_SMTP_PASSWORD=...
QUARKUS_DATASOURCE_PASSWORD=...
----
+
und vor dem Start laden (`set -a; source /etc/konfplan/prod.env; set +a`), bzw. bei Betrieb als systemd-Service über `EnvironmentFile=/etc/konfplan/prod.env` in der Unit-Datei.
====

== 5. Besonderheiten & Einschränkungen

[IMPORTANT]
====
* **Reflection:** Quarkus kümmert sich um die meiste Reflection-Konfiguration. Wenn du jedoch eigene Klassen nutzt, die erst zur Laufzeit via Reflection geladen werden (selten nötig bei diesem Projekt), müssen diese explizit registriert werden.
* **Build-Ressourcen:** Der Native Build benötigt viel CPU und RAM (ca. 4-8 GB freier Speicher empfohlen).
* **Externe Templates:** Stelle sicher, dass das Verzeichnis in `TEMPLATES_DIR` für den Anwender lesbar ist. Bei der Verwendung von Docker muss dieser Pfad als Volume gemountet werden.
====

== 6. Kombination mit Docker

Oft wird das native Executable direkt in ein minimales Docker-Image (z.B. `ubi-micro` oder `scratch`) verpackt. Der entsprechende Docker-Build-Befehl lautet:

[source,bash]
----
docker build -f backend/src/main/docker/Dockerfile.native -t konfplan/backend-native backend
----

NOTE: Der Build-Context ist `backend` (nicht das Repo-Root), da `Dockerfile.native` die Runner-Datei relativ als `target/*-runner` kopiert.

== 7. Build für eine andere Plattform/Architektur (Cross-Build)

Ein natives Executable ist immer für ein bestimmtes Betriebssystem und eine bestimmte CPU-Architektur kompiliert (z.B. `linux/aarch64` vs. `linux/amd64`) und läuft nur dort. Ein auf Apple Silicon gebautes Binary läuft z.B. nicht auf einem x86_64-Linux-Server.

Für einen Cross-Build bleibt man beim Container-Build (Variante B), gibt Docker aber explizit die Ziel-Plattform mit. Docker Desktop bringt dafür QEMU-Emulation für Fremdarchitekturen bereits mit:

[source,bash]
----
./mvnw clean package -Dnative -DskipTests \
  -Dquarkus.native.container-runtime-options=--platform=linux/amd64
----

Damit läuft der Builder-Container per Emulation für `linux/amd64` und erzeugt ein passendes Runner-Executable.

Beim anschließenden Docker-Image-Build muss die Ziel-Plattform ebenfalls angegeben werden (sonst wird die Host-Architektur verwendet):

[source,bash]
----
docker buildx build --platform linux/amd64 \
  -f backend/src/main/docker/Dockerfile.native \
  -t konfplan/backend-native:amd64 backend
----

NOTE: Das Basis-Image (`ubi8/ubi-minimal`) ist Multi-Arch, `buildx` zieht automatisch das passende Manifest für die angegebene Plattform.
