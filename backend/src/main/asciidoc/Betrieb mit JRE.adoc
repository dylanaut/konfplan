= KonfPlan: Entwicklungs- und Produktions-Workflow
:toc: left
:icons: font
:source-highlighter: highlightjs

Dieses Dokument beschreibt, wie das Backend (Quarkus) und das Frontend (Vue/Vite) mithilfe von *Quarkus Quinoa* integriert sind und wie sie gestartet werden.

== 1. Entwicklungsmodus (Dev Mode)

Im Entwicklungsmodus sorgt die Erweiterung **Quinoa** dafür, dass beide Welten miteinander verknüpft werden.

=== Automatischer Start
Wenn du im Verzeichnis `backend/` den Befehl ausführst:

[source,bash]
----
./mvnw quarkus:dev
----

Passiert folgendes automatisch:
1. Das **Quarkus-Backend** startet auf Port `9000`.
2. Quinoa erkennt das Frontend-Verzeichnis (`../frontend`) und startet den **Vite-Dev-Server** auf Port `5173`.
3. Quarkus agiert als **Proxy**: Du kannst die Anwendung unter `http://localhost:9000` aufrufen. Anfragen, die kein API-Pfad sind, werden intern an das Frontend weitergeleitet.

[TIP]
====
Sollte der Frontend-Server nicht starten, stelle sicher, dass die Abhängigkeiten installiert sind:
[source,bash]
----
cd frontend
npm install
----
====

=== Manueller Start des Frontends
Falls du ausschließlich am UI arbeiten möchtest, kannst du das Frontend auch separat starten:

[source,bash]
----
cd frontend
npm run dev
----
Das UI ist dann direkt unter `http://localhost:5173` erreichbar (erfordert CORS-Konfiguration im Backend).

== 2. Produktionsbetrieb (PROD)

Im Produktionsbetrieb verschmelzen Frontend und Backend zu einer einzigen Einheit. Es wird kein separater Vite-Server mehr benötigt.

=== Build-Prozess
Der Build sollte vom **Wurzelverzeichnis** des Projekts ausgeführt werden, damit das Maven-Multi-Module-System greift:

[source,bash]
----
./mvnw clean package -DskipTests
----

* **Was passiert hier?** Maven ruft `npm run build` im Frontend-Ordner auf. Die fertigen statischen Dateien (aus `dist/`) werden automatisch in das Java-Artefakt (`JAR`) des Backends kopiert.

=== Starten der Anwendung

[IMPORTANT]
====
Im PROD-Profil gibt es keine DevServices mehr – PostgreSQL und ein SMTP-Server müssen daher **vor** dem Start selbst bereitgestellt werden. Dafür gibt es das Hilfsscript:

[source,bash]
----
./db/ensure_prod_infra.sh
----

Es startet idempotent (per Docker-Label wiedererkennbar) einen `postgres:18`- und einen `axllent/mailpit`-Container (lokaler Ersatz für den echten Brevo-SMTP-Server) und gibt am Ende den passenden `export`-Block für den Start aus.
====

Nach dem Build startest du nur noch das Backend:

[source,bash]
----
java -jar backend/target/quarkus-app/quarkus-run.jar
----

* **Das Ergebnis:**
** Die gesamte Anwendung (inkl. UI) läuft auf einem einzigen Port (Standard: `9000`).
** Das Frontend wird unter `http://localhost:<PORT>/` ausgeliefert.
** Die API ist im DEV Mode unter `http://localhost:<PORT>/q/dev-ui` erreichbar.
** Das rohe OpenAPI Schema ist unter `http://localhost:<PORT>/q/openapi` abrufbar.

=== Zugangsdaten für Produktion (Mailserver, DB)

Im echten Produktivbetrieb werden Datenbank-Zugangsdaten und die Zugangsdaten des Mailservers (`BREVO_SMTP_USER`/`BREVO_SMTP_PASSWORD`, siehe `%prod.quarkus.mailer.username`/`.password` in `application.properties`) über Umgebungsvariablen übergeben – analog zu `QUARKUS_DATASOURCE_*` in Abschnitt 3.

[IMPORTANT]
====
Diese Zugangsdaten dürfen **nicht** im Git-Repository landen. Zwei gängige Wege, sie trotzdem bereitzustellen:

* **CI/CD-Pipeline (GitLab):** Als *maskierte* + *geschützte* CI/CD-Variablen unter *Project → Settings → CI/CD → Variables* anlegen. Der `deploy_to_production`-Job in `.gitlab-ci.yml` reicht sie dann per `-e BREVO_SMTP_USER=${BREVO_SMTP_USER}` an den entfernten `docker run`-Aufruf durch.
* **Direkt auf dem Server** (z.B. bei einem manuellen Start): eine Datei außerhalb des Repos anlegen, z.B. `/etc/konfplan/prod.env` mit `chmod 600`:
+
[source,bash]
----
BREVO_SMTP_USER=...
BREVO_SMTP_PASSWORD=...
QUARKUS_DATASOURCE_PASSWORD=...
----
+
und vor dem Start laden (`set -a; source /etc/konfplan/prod.env; set +a`), bzw. bei Betrieb als systemd-Service über `EnvironmentFile=/etc/konfplan/prod.env` in der Unit-Datei.
====

== 3. Relevante Konfiguration

Die Steuerung erfolgt in der Datei `/Users/kreyj/Java/berufsorientierung/konfplan/backend/src/main/resources/application.properties`:

[source,properties]
----
# Pfad zum Frontend relativ zum Backend-Modul
quarkus.quinoa.ui-dir=../frontend

# Port des Vite-Dev-Servers für die Proxy-Weiterleitung
quarkus.quinoa.dev-server.port=5173

# Verzeichnis der gebauten Frontend-Dateien (für Prod-Build)
quarkus.quinoa.build-dir=dist

# CORS-Einstellungen für die lokale Entwicklung
quarkus.http.cors.enabled=true
quarkus.http.cors.origins=http://localhost:5173
----

[IMPORTANT]
====
Stelle sicher, dass **Node.js** und **npm** auf deinem System installiert sind, da Quinoa diese Tools während des Maven-Builds aufruft.
====

== 4. Installation auf UTM (lokale Virtualisierung auf Mac)

Hier kommen die Schritte, um die Quarkus Anwendung konfplan samt Abhängigkeiten zu installieren und im PROD Modus starten,
sowohl native als auch mit JRE.

=== JVM/JRE-Modus unter Debian/Ubuntu

Für den JVM/JRE-Modus existieren zwei bereits vorhandene, fertige Wege im Repo.

==== Weg A: Docker Compose (empfohlen für UTM – bereits explizit dafür gebaut)

`deploy/docker-compose.yml` hat genau ein #local#-Profil für diesen Fall (Mac+UTM, kein TLS nötig, im Gegensatz zum #public#-Profil für Hetzner+Caddy). Läuft im JVM-Modus (Image ghcr.io/dylanaut/konfplan, baut auf Dockerfile.jvm).

====   Weg B: .deb-Pakete (nativer systemd-Betrieb, kein App-Container)

Ubuntu ist Debian-basiert, die Paketnamen (openjdk-21-jre-headless, minizinc, postgresql, docker.io) sind identisch:
[source,shell]
----
git clone https://github.com/dylanaut/konfplan.git && cd konfplan
./install.sh
----

Baut Frontend+Backend, erstellt/installiert alle 4 .deb-Pakete (konfplan-postgresql → konfplan-keycloak → konfplan-mailpit →
konfplan), siehe packaging/debian/README.md. Läuft ebenfalls im JVM-Modus (fast-jar, kein Native Image).

. Native Image (GraalVM) – manuell, noch nicht paketiert

backend/src/main/asciidoc/Betrieb mit Native Image.adoc beschreibt den Build:

[source,shell]
----
# Cross-Build von macOS für linux/amd64 (falls die VM x86_64 ist) bzw. ohne
# --platform, falls die VM aarch64 ist (Apple-Silicon-Host, UTM meist gleiche Arch):
./mvnw clean package -Dnative -DskipTests \
    -Dquarkus.native.container-runtime-options=--platform=linux/amd64
----

Ergebnis ist ein `-runner`-Binary, das du auf die VM kopierst und dort mit Env-Vars (DB_*, KC_SERVER_URL, KC_REALM,
KC_ADMIN_CLI_SECRET, BREVO_SMTP_*/Mailpit) startest – kein JRE auf der VM nötig.

. Native Image unter Debian/Ubuntu

  Auf der Ubuntu-VM:
  sudo apt-get update && sudo apt-get install -y docker.io docker-compose-plugin git
  git clone https://github.com/dylanaut/konfplan.git && cd konfplan/deploy
  ./bootstrap.sh          # generiert Secrets (DB, Keycloak-Admin/Client) serverseitig
  docker compose --profile local up -d
  Details/Troubleshooting: backend/src/main/asciidoc/Deployment-DockerCompose.adoc.
