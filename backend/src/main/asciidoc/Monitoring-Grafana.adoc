= KonfPlan: Monitoring mit Prometheus/Grafana
:toc:

== Überblick

KonfPlan exponiert Metriken im Prometheus-Textformat unter `/q/metrics` - auf einem eigenen
**Management-Port (9001)**, getrennt vom öffentlichen App-Port (9000).

[WARNING]
====
Port 9001 nicht öffentlich routen (siehe `Deployment-DockerCompose.adoc` -> "Monitoring /
Metriken"). Der Endpunkt ist unauthentifiziert und liefert sowohl JVM-interne Details als auch
Nutzungszahlen.
====

== Grafisch darstellen bei reinem SSH-Zugriff (Profil "monitoring")

Für einen Cloud-Server, der nur per SSH erreichbar ist, laufen Prometheus + Grafana als
zusätzliche Services im selben `docker-compose.yml`-Stack (`deploy/prometheus.yml`,
`deploy/grafana/`):

* Prometheus erreicht `app:9001` über das interne Docker-Netzwerk - Port 9001 wird dafür
  **nicht** auf den Host oder das Internet gemappt.
* Grafana ist wie `app`/`mailpit` nur an `127.0.0.1` gebunden (Variable `GRAFANA_PORT_BINDING`
  in `.env`, Standard `127.0.0.1:3000:3000`) - Zugriff ausschließlich per SSH-Tunnel, nie
  öffentlich über Caddy geroutet.
* Die Prometheus-Datenquelle und ein vorkonfiguriertes Dashboard ("KonfPlan Übersicht", alle
  Metriken aus diesem Dokument) werden beim Start automatisch provisioniert - kein manuelles
  Einrichten in der Grafana-UI nötig.

[source,bash]
----
# Auf dem Server (zusätzlich zu den ohnehin laufenden Profilen, z.B. "public"):
docker compose --profile public --profile monitoring up -d

# Lokal: Tunnel zu Grafana aufbauen, dann im eigenen Browser öffnen
ssh -L 3000:127.0.0.1:3000 user@server
# -> http://localhost:3000 im lokalen Browser
----

Erster Login: `admin` / `admin` - Grafana erzwingt beim ersten Login eine Passwortänderung.

Für einen schnellen Check ohne Grafana reicht auch ein direkter Blick auf die Rohdaten:
[source,bash]
----
ssh user@server
cd /pfad/zu/deploy && docker compose exec app curl -s http://localhost:9001/q/metrics | grep konfplan_
----

Kommt automatisch mit `quarkus-micrometer-registry-prometheus` (keine eigene Instrumentierung
nötig):

* JVM-Speicher (`jvm_memory_used_bytes`, `jvm_memory_max_bytes` je Heap-/Non-Heap-Bereich), GC-Pausen (`jvm_gc_pause_seconds`), Thread-Anzahl (`jvm_threads_live_threads`)
* HTTP-Request-Metriken (`http_server_requests_seconds_count`/`_sum`, nach Pfad/Methode/Status)
* DB-Connection-Pool (Agroal, `agroal_active_count`, `agroal_available_count`)

== Container-Uptime/-Restarts (cAdvisor)

Docker Compose selbst liefert keine Prometheus-Metriken zu Container-Lebenszyklen (Uptime,
Neustarts) - dafür läuft im Profil "monitoring" zusätzlich
https://github.com/google/cadvisor[cAdvisor], das diese Daten direkt aus den
Docker-/Cgroup-Informationen des Hosts liest und unter `container_start_time_seconds` (Startzeit
seit Unix-Epoche, pro Container) exponiert. Panel "Container-Uptime (Zeit seit letztem Start)" im
Dashboard zeigt `time() - container_start_time_seconds{...}` - ein plötzlicher Abfall auf nahe 0
markiert einen (Neu-)Start.

Nur lesende Mounts (`:ro`), kein `privileged: true` - reicht für Start-/Laufzeit-Metriken, nicht
aber für alle von cAdvisor grundsätzlich unterstützten Metriken (z.B. manche Disk-I/O-Details).

[NOTE]
====
Der Docker-Socket muss explizit gemountet werden (`/var/run/docker.sock:/var/run/docker.sock:ro`)
- ein Mount des gesamten `/var/run`-Verzeichnisses reicht nicht: cAdvisors Docker-Integration
registriert sich dann nicht ("Cannot connect to the Docker daemon"), und alle Metriken zeigen nur
rohe Cgroup-Pfade (`id="/docker"` usw.) statt einzelner Container mit Namen/Labels - per Live-Test
verifiziert.
====

== Custom-Metriken (KonfPlan-spezifisch)

[cols="2,1,3", options="header"]
|===
| Metrik | Typ | Bedeutung

| `konfplan_users_online{role}`
| Gauge
| Anzahl Nutzer mit Backend-Aktivität innerhalb der letzten 5 Minuten, gruppiert nach `role` (`ADMIN`/`REFERENT`/`TEILNEHMER`). Aktualisiert bei jedem authentifizierten Request (`UserActivityTrackingFilter`), rein In-Memory - kein DB-Zugriff im Hot-Path.

| `konfplan_session_duration_seconds{role}`
| Timer (`_count`, `_sum`, `_max`)
| Verweilzeit eines Nutzers im System: Zeit zwischen erster und letzter Aktivität eines zusammenhängenden Besuchs (Besuch gilt nach 5 Minuten Inaktivität als abgeschlossen). Durchschnitt = `_sum / _count`.

| `konfplan_login_failures_total{role}`
| Counter
| Fehlgeschlagene Anmeldeversuche, gruppiert nach Rolle. Rolle `UNKNOWN`, wenn der eingegebene Benutzername keinem existierenden `Nutzer` entspricht. Gespeist aus Keycloaks Realm-Events (`LOGIN_ERROR`), gepollt einmal pro Minute - siehe <<datenquelle>>.
|===

[[datenquelle]]
== Woher die Daten kommen

* **Online-Nutzer/Verweilzeit**: rein im KonfPlan-Backend selbst gemessen (`UserActivityTracker`), bewusst NICHT anhand der Keycloak-Session-Laufzeit (die bleibt auch bei Inaktivität "eingeloggt" und würde die Verweilzeit verfälschen).
* **Fehlgeschlagene Logins**: passieren bei Keycloak, nie im Backend selbst - Keycloak lehnt falsche Zugangsdaten ab, bevor die App ein Token sieht. `FailedLoginMetricsPoller` fragt daher periodisch Keycloaks Realm-Events ab (`GET /admin/realms/{realm}/events?type=LOGIN_ERROR`), löst den Benutzernamen zur KonfPlan-Rolle auf und zählt es als Metrik. Dafür müssen Realm-Events aktiviert sein (`eventsEnabled`, `enabledEventTypes: ["LOGIN_ERROR"]`, `eventsExpiration` für automatisches Aufräumen) und der Admin-CLI-Service-Account braucht die Client-Rolle `view-events` auf `realm-management` - beides wird sowohl für Neuanlagen (Realm-JSON) als auch für bestehende Deployments (`ProdKeycloakRealmSyncService`, idempotent bei jedem Start) sichergestellt.

== Beispiel-PromQL-Queries für Grafana

Online-Nutzer aktuell, nach Rolle:
[source]
----
konfplan_users_online
----

Peak an Online-Nutzern der letzten 24 Stunden (Peaks werden bewusst nicht serverseitig berechnet - Grafana kann das aus der Zeitreihe ableiten):
[source]
----
max_over_time(konfplan_users_online[24h])
----

Durchschnittliche Verweilzeit (Minuten) über das letzte Stunden, nach Rolle:
[source]
----
rate(konfplan_session_duration_seconds_sum[1h]) / rate(konfplan_session_duration_seconds_count[1h]) / 60
----

Fehlgeschlagene Logins pro Stunde, nach Rolle:
[source]
----
increase(konfplan_login_failures_total[1h])
----

Belegung des DB-Connection-Pools:
[source]
----
agroal_active_count / (agroal_active_count + agroal_available_count)
----

Container-Uptime seit letztem (Neu-)Start, je Kern-Container:
[source]
----
time() - container_start_time_seconds{container_label_com_docker_compose_service=~"app|keycloak|postgres"}
----

== Bekannte Stolperfallen (per Live-Test gegen Keycloak 26.7.0 verifiziert)

* Keycloaks `GET /admin/realms/{realm}/events`-Endpunkt akzeptiert für den `direction`-Parameter nur klein geschriebene Werte (`asc`/`desc`) - `ASC`/`DESC` liefert `400 Bad Request`, obwohl der Java-Admin-Client dafür einen ungeprüften `String`-Parameter anbietet.
* `dateFrom`/`dateTo` können sowohl als Datum (`yyyy-MM-dd`) als auch als Unix-Zeitstempel in Millisekunden übergeben werden - beide Formate werden akzeptiert.
* Ohne die Client-Rolle `view-events` (siehe oben) liefert derselbe Endpunkt `403 Forbidden`, nicht `401` - leicht mit einem generellen Auth-Problem zu verwechseln.
* In `quarkus:dev` liefert `/q/metrics` `400 Bad Request`, wenn der `Host`-Header nicht auf `localhost`/`127.0.0.1` lautet (z.B. beim Testen mit einem eigenen Prometheus-Container gegen `host.docker.internal:9001`) - Ursache ist Quarkus' `LocalHostOnlyFilter` (Paket `quarkus-vertx-http-dev`), eine reine Dev-Mode-Schutzmaßnahme gegen DNS-Rebinding. Im gepackten/Prod-Image (kein `-dev`-Artefakt auf dem Klassenpfad) tritt das nicht auf - für lokale Tests gegen `quarkus:dev` daher `localhost`/`127.0.0.1` als Scrape-Ziel verwenden, nicht `host.docker.internal`.
