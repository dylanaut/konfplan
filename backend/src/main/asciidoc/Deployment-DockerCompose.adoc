== Überblick

Dieses Verfahren startet alle Komponenten (App, PostgreSQL, Keycloak, optional Caddy/Mailpit) über ein einziges `docker-compose
.yml` unter `deploy/` - identisch nutzbar lokal in einer UTM-VM auf dem Mac (https://kofler.info/ubuntu-24-04-utm/[Anleitung
Kofler], Downloads unter https://cdimage.ubuntu.com//ubuntu/noble/daily-live/current/[cdimage.ubuntu]) und auf einem Cloud-Server
wie Hetzner.
Es ist ein zusätzliches, alternatives Verfahren zum bestehenden `.deb`/systemd-Weg (`packaging/debian/`, `install.sh`) - beide bleiben unabhängig voneinander bestehen.

Passwörter (DB, Keycloak-Admin, Keycloak-Admin-CLI-Client-Secret) werden **niemals** im Repo, in `docker-compose.yml` oder in `.env` hinterlegt. `deploy/bootstrap.sh` generiert sie beim ersten Lauf direkt auf dem jeweiligen Host in `deploy/secrets/*.txt` (chmod 644, `secrets/`-Verzeichnis selbst chmod 700, .gitignore'd) und bindet sie per Docker-Compose-File-Secrets read-only in die Container - nichts wird übertragen, nichts landet in `docker inspect`/Prozessumgebung. 644 statt 600, da die App-/Keycloak-Images als Nicht-root-User laufen (z.B. UID 185) und die Host-Dateirechte beim Bind-Mount erhalten bleiben - bei 600 gäbe es dort "Permission denied".

== Voraussetzungen

* Docker Engine + Compose-Plugin (`docker compose version` sollte funktionieren)
* `openssl` (für die Secret-Generierung, auf macOS/Debian bereits vorhanden)
* Für das Profil `public` (Hetzner): ein DNS-A-Record auf die Server-IP (siehe unten)

== Verzeichnis `deploy/`

[cols="1,3",options="header"]
|===
| Datei | Zweck
| `docker-compose.yml` | Alle Services (App, Postgres, Keycloak, Caddy, Mailpit)
| `bootstrap.sh` | Generiert fehlende Secrets, rendert das Keycloak-Realm-Template
| `.env.example` | Nicht-geheime Konfiguration (Hostnames, Ports, Image-Tag) - nach `.env` kopieren
| `keycloak-realm.template.json` | Realm-Vorlage (Rollen/Clients), Platzhalter für Secret + Domain
| `Caddyfile` | Reverse-Proxy-Konfiguration für Profil `public` (automatisches Let's Encrypt)
| `postgres-init/` | Legt beim allerersten Start zusätzlich die `keycloak`-Datenbank an
|===

Zur Laufzeit/gitignored erzeugt: `.env`, `secrets/*.txt`, `keycloak-realm.generated.json`.

== Secrets-Handling im Detail

`bootstrap.sh` ist idempotent: einmal generierte Secret-Dateien werden bei erneutem Aufruf
**nicht** überschrieben (ein Redeploy rotiert also keine Passwörter versehentlich).
Ablauf:

1. Generiert (falls nicht vorhanden) `secrets/db_password.txt`, `secrets/keycloak_admin_password.txt`,
`secrets/keycloak_admin_cli_secret.txt` via `openssl rand -hex 32` (Hex statt Base64, damit die Werte auch in URL-Query-Parametern/form-urlencoded Requests ohne Sonderfälle funktionieren - Base64 enthält `+`, `/`, `=`).
Diese drei erzeugt/braucht ausschließlich diese Anwendung selbst.
2. Legt (falls nicht vorhanden) eine **leere** `secrets/brevo_smtp_password.txt` an - der Wert kommt von außen (dein Brevo-Account, siehe unten) und wird deshalb nie zufällig generiert.
3. Rendert `keycloak-realm.template.json` → `keycloak-realm.generated.json`: ersetzt
`__ADMIN_CLI_SECRET__` durch den generierten Wert und `__APP_PUBLIC_URL__` durch
`APP_PUBLIC_URL` aus `.env` (Redirect-URIs des Frontend-Clients).

=== Mailversand-Zugangsdaten (Brevo)

`BREVO_SMTP_USER` (dein Brevo-Login) kommt als normale, nicht-geheime Variable aus `.env` - siehe Kommentar dort.
Das zugehörige Passwort ist ein echter SMTP-Schlüssel aus deinem Brevo-Account (https://app.brevo.com → *SMTP & API* → *SMTP-Schlüssel*) und muss **manuell**
eingetragen werden, `bootstrap.sh` kann ihn nicht erraten:

[source,bash]
----
echo '<dein-brevo-smtp-schluessel>' > secrets/brevo_smtp_password.txt
chmod 644 secrets/brevo_smtp_password.txt
----

`bootstrap.sh` warnt, falls `BREVO_SMTP_USER` gesetzt, die Secret-Datei aber noch leer ist.
Alternative ohne echten Brevo-Account: Profil `mailpit` statt `BREVO_SMTP_USER` nutzen (kein echter Versand, Test-Postfach unter `http://localhost:8025`) - dann bleibt die leere Platzhalter-Datei einfach unbenutzt.

In `docker-compose.yml` werden die Secrets per `secrets:`-Block eingebunden und dort, wo das Image selbst kein `_FILE`-Suffix unterstützt (Keycloak, App), per überschriebenem `command` aus
`/run/secrets/*` gelesen und vor dem eigentlichen Start exportiert.
PostgreSQL unterstützt
`POSTGRES_PASSWORD_FILE` nativ.

== Lokal auf macOS mit UTM

Sinnvoll, um das komplette Compose-Setup vor einem echten Cloud-Deploy zu testen.

. UTM installieren (`brew install --cask utm` oder von https://mac.getutm.app).
. Neue VM erstellen: *Virtualize* (nicht Emulate, da Apple Silicon) → Linux → Debian 13 oder Ubuntu 24.04 ARM64-Server-ISO.
Netzwerk-Modus *Shared Network* reicht, damit die VM per SSH und über einen Port-Forward erreichbar ist.
. In der VM: Docker installieren (offizielles Docker-Repo, nicht `docker.io` aus den Distributions-Paketen, da das Compose-Plugin sonst fehlt):
+
[source,bash]
----
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker $USER   # neu einloggen, damit die Gruppe greift
----
. Repo (oder nur `deploy/`) auf die VM bringen, z.B. per `git clone` oder `scp -r deploy/ vm:~/konfplan-deploy/`.
. Im `deploy/`-Verzeichnis:
+
[source,bash]
----
cp .env.example .env    # Standardwerte reichen lokal meist unveraendert
./bootstrap.sh
docker compose up -d
----
. App unter `http://<VM-IP-oder-localhost>:9000`, Keycloak-Admin-Konsole unter
`http://<VM-IP-oder-localhost>:8080/auth` erreichbar (Login: `admin` / Inhalt von
`secrets/keycloak_admin_password.txt`). Keycloak läuft immer (auch lokal, unabhängig vom
Profil `public`) unter dem Pfad `/auth` (`KC_HTTP_RELATIVE_PATH`), damit Prod und lokal
identisch konfiguriert sind.

== Hetzner Cloud (öffentlich erreichbar)

=== Server erstellen

Über die Hetzner-Cloud-Console oder die `hcloud`-CLI, z.B.:

[source,bash]
----
hcloud server create --name konfplan --type cx22 --image debian-13 --ssh-key <dein-key-name>
----

Ein `cx22` (2 vCPU/4 GB) reicht für App+Postgres+Keycloak im Kleinbetrieb.

=== DNS

Ein A-Record auf die Server-IP anlegen. Keycloak teilt sich die Domain mit der App und läuft
unter dem Pfad `/auth` (`KC_HTTP_RELATIVE_PATH`, siehe `Caddyfile`) - kein eigener Hostname
mehr nötig, falls der DNS-/Cloud-Betreiber keine weiteren A-Records erlaubt:

[source]
----
konfplan.<deine-domain>       A   <server-ip>
----

=== Firewall

Nur SSH, HTTP und HTTPS öffentlich erlauben - Postgres/Keycloak/App-Ports NICHT (sie sind ohnehin per `127.0.0.1:...`-Bindung in `docker-compose.yml` schon nicht von außen erreichbar, siehe Kommentar dort; die Firewall ist die zweite Verteidigungslinie).

[source,bash]
----
hcloud firewall create --name konfplan-fw
hcloud firewall add-rule konfplan-fw --direction in --protocol tcp --port 22 --source-ips 0.0.0.0/0,::/0
hcloud firewall add-rule konfplan-fw --direction in --protocol tcp --port 80 --source-ips 0.0.0.0/0,::/0
hcloud firewall add-rule konfplan-fw --direction in --protocol tcp --port 443 --source-ips 0.0.0.0/0,::/0
hcloud firewall apply-to-resource konfplan-fw --type server --server konfplan
----

=== Docker installieren, Deploy übertragen

Wie im UTM-Fall (`curl -fsSL https://get.docker.com | sudo sh`), dann per `scp`/`git clone` das
`deploy/`-Verzeichnis auf den Server bringen.

=== `.env` für Profil `public` ausfüllen

[source,bash]
----
cp .env.example .env
----

In `.env` zusätzlich (siehe auskommentierte Zeilen dort):

[source]
----
APP_HOSTNAME=konfplan.<deine-domain>
APP_PUBLIC_URL=https://konfplan.<deine-domain>
KEYCLOAK_PUBLIC_URL=https://konfplan.<deine-domain>/auth
ACME_EMAIL=<deine-email>          # Let's-Encrypt-Kontaktadresse
BREVO_SMTP_USER=<dein-brevo-login>  # oder Profil "mailpit" statt echtem SMTP nutzen
----

=== Starten

[source,bash]
----
./bootstrap.sh public
docker compose --profile public up -d
----

Caddy bezieht beim ersten Start automatisch ein Let's-Encrypt-Zertifikat für die Domain (dauert wenige Sekunden, sichtbar in `docker compose logs caddy -f`).
App/Keycloak sind dann NICHT mehr direkt per Port erreichbar, nur noch über Caddy (Port 80/443).

=== Smoke-Test

[source,bash]
----
curl -sI https://konfplan.<deine-domain>/
curl -s https://konfplan.<deine-domain>/auth/realms/konfplan/.well-known/openid-configuration | jq .issuer
----

== Update / Redeploy

[source,bash]
----
docker compose pull app          # neues Image von ghcr.io
docker compose up -d app         # nur die App neu starten, DB/Keycloak laufen weiter
----

`bootstrap.sh` vorher erneut auszuführen ist unschädlich (überschreibt keine bestehenden Secrets), aber i.d.R. nicht nötig, solange sich `.env` nicht geändert hat.

=== Lokal gebautes Image statt `ghcr.io`-Release verwenden

Für Tests eines noch nicht gemergten Standes, ohne über die CI (`.github/workflows/ci.yml`) zu gehen. Zwei Varianten:

**Option A - Image lokal bauen und selbst nach `ghcr.io` pushen (empfohlen, nutzt den bestehenden `IMAGE_TAG`-Mechanismus unverändert):**

[source,bash]
----
# 1. Lokal wie die CI bauen (identisch zu ci.yml)
./mvnw clean install -DskipTests
cd backend

# 2. Image mit demselben Dockerfile/Kontext wie CI bauen, eigenen Tag vergeben
docker build -f src/main/docker/Dockerfile.jvm -t ghcr.io/dylanaut/konfplan:local-test .

# 3. Bei ghcr.io einloggen (GitHub PAT mit Scope 'write:packages') und pushen
echo $GH_PAT | docker login ghcr.io -u <dein-github-user> --password-stdin
docker push ghcr.io/dylanaut/konfplan:local-test
----

Auf dem Server danach in `.env`:

[source]
----
IMAGE_TAG=local-test
----

und wie gewohnt `docker compose pull app && docker compose up -d app`. `docker-compose.yml` muss dafür nicht angepasst werden, da `app.image` bereits `ghcr.io/dylanaut/konfplan:${IMAGE_TAG:-latest}` verwendet.

**Option B - ganz ohne Registry, Image direkt auf den Server kopieren:**

[source,bash]
----
# lokal
docker build -f backend/src/main/docker/Dockerfile.jvm -t ghcr.io/dylanaut/konfplan:local-test backend
docker save ghcr.io/dylanaut/konfplan:local-test | gzip | ssh <user>@<server> "gunzip | docker load"
----

Auf dem Server ebenfalls `IMAGE_TAG=local-test` in `.env` setzen, aber `docker compose up -d app`
**ohne vorheriges `docker compose pull`** aufrufen - sonst versucht Compose, `local-test` von
`ghcr.io` zu ziehen und schlägt fehl, da der Tag dort nicht existiert.

WARNING: In beiden Fällen danach `IMAGE_TAG` wieder auf `latest` zurückstellen, sonst bleibt der Server dauerhaft auf dem manuell gebauten Stand und bekommt keine künftigen CI-Releases mehr.

== Der eine echte Bestandsaccount

Anders als bei der Keycloak-Migration selbst (siehe `keycloak-migration.adoc` - dort gab es praktisch keine echten Bestandsnutzer) betrifft das bei einem *erstmaligen* Produktions-Deploy genau einen Fall: den Bootstrap-Admin aus `V2__data.sql` (`juergenkrey`).
Dieser Account existiert nur als Datenbankzeile, nicht in Keycloak - er muss einmalig manuell über die Keycloak-Admin- Konsole
angelegt werden (Login-Name muss mit `juergenkrey` übereinstimmen, Rolle `ADMIN`). +
(Siehe Ubuntu-Frischinstallation.adoc, "Erster Login-Account")

== Persistenz über Neustarts hinweg

Keycloak speichert seinen gesamten Zustand (Nutzer, Rollen-Zuweisungen, Client-Konfiguration) in seiner eigenen PostgreSQL-Datenbank (`KC_DB=postgres`, siehe `docker-compose.yml`) - nicht im Container selbst.
Diese Datenbank liegt im benannten Docker-Volume `deploy_postgres-data`, das
`docker compose stop`/`restart`/`down` (ohne `-v`) unberührt lässt; nur `docker compose down -v`
oder ein manuelles `docker volume rm` löschen es.
Der `--import-realm`-Flag beim Keycloak-Start importiert das Realm nur beim allerersten Mal (danach: "Realm 'konfplan' already exists.
Import skipped") - spätere Starts lesen ausschließlich den bereits persistierten Zustand.

Konkret verifiziert: Admin-Login + ein eigens angelegter Testnutzer überleben einen vollen
`docker compose down` (ohne `-v`) + `up` unverändert.

== Backup-Hinweise

* **PostgreSQL**: Volume `deploy_postgres-data` enthält sowohl die App- als auch die Keycloak-Datenbank.
Klassischer `pg_dump`/Volume-Snapshot reicht für einen Kleinbetrieb.
* **Keycloak-Realm**: `docker compose exec keycloak /opt/keycloak/bin/kc.sh export --dir /tmp/export --realm konfplan`
exportiert den aktuellen (durch Admin-UI-Änderungen ggf. abweichenden) Realm-Zustand - nützlich vor größeren Änderungen, ersetzt aber kein DB-Backup.
* **Secrets**: `deploy/secrets/` ist der einzige Ort, an dem die Passwörter existieren - bei einem Server-Wechsel/Wiederherstellung müssen sie mitgesichert werden (z.B. verschlüsselt, getrennt von einem reinen DB-Backup).

== Monitoring / Metriken

KonfPlan exponiert Prometheus-Metriken (Ressourcenverbrauch, Online-Nutzer, Verweilzeit, fehlgeschlagene Logins nach Rolle) unter `/q/metrics` auf einem eigenen **Management-Port (9001)**, getrennt vom öffentlichen App-Port (9000) - siehe `Monitoring-Grafana.adoc` für die vollständige Metrik-Referenz und Beispiel-Queries.

[WARNING]
====
Port 9001 darf **nicht** über Caddy/eine Cloud-Firewall öffentlich geroutet werden - er liefert unauthentifiziert JVM-interne Details sowie Nutzungszahlen. Prometheus muss ihn intern erreichen (z.B. im selben Docker-Netzwerk, per SSH-Tunnel, oder über ein separates internes Netzwerk-Interface) statt über die öffentliche Domain.
====

== Ausgehende Server-IP überwachen (Brevo-Allowlist)

Cloud-Server ohne feste IP-Adresse können ihre ausgehende IP ändern (z.B. nach einem Server-Wechsel oder -Neuaufbau). Brevo blockt den SMTP-Zugang dann mit `525 5.7.1 Unauthorized IP address` in den `keycloak`-Logs, bis die neue IP manuell unter *SMTP & API → Authorized IPs* auf https://app.brevo.com nachgetragen wird - **kein KonfPlan-/Code-Problem**, rein eine Brevo-Kontoeinstellung. Brevo bietet dafür keine API zur automatischen Pflege der Liste, nur die Web-Oberfläche.

`deploy/check-outbound-ip.sh` erkennt eine solche Änderung frühzeitig und schickt eine Push-Benachrichtigung über https://ntfy.sh[ntfy.sh] - bewusst unabhängig von Brevo/SMTP, damit die Meldung auch ankommt, wenn genau die IP-Änderung gerade den Mailversand blockiert.

Einrichtung:

. Einen zufälligen, nicht erratbaren Topic-Namen wählen (ntfy.sh-Themen sind ohne Zusatzauthentifizierung öffentlich lesbar für jeden, der den Namen kennt) und in der ntfy-App/-Website abonnieren.
. In `deploy/.env` eintragen: `NTFY_TOPIC=<dein-topic-name>`
. Cron-Eintrag auf dem Server (alle 30 Minuten reicht):
+
[source,bash]
----
*/30 * * * * /pfad/zu/deploy/check-outbound-ip.sh >> /var/log/konfplan-ip-check.log 2>&1
----

Bei einer Meldung ohne automatische Brevo-Eintragung (siehe unten): die im Push-Text genannte neue IP in Brevo nachtragen - danach funktioniert der Mailversand wieder ohne Neustart von irgendetwas.

[NOTE]
====
Die dauerhafte Lösung ist eine feste IP-Adresse für den Server (bei Hetzner Cloud z.B. eine https://docs.hetzner.com/cloud/floating-ips/overview/[Floating IP]) - dann entfällt das Problem komplett. Das erfordert ggf. zusätzliche Routing-Konfiguration, damit ausgehender Traffic tatsächlich über die Floating IP läuft, und ist nicht Teil dieses Skripts.
====

=== Optional: Brevo-Eintragung automatisieren (Playwright)

Falls sich die IP häufig/täglich ändert, kann `deploy/check-outbound-ip.sh` die neue IP zusätzlich automatisch bei Brevo eintragen (per Playwright, da Brevo dafür keine API bietet - nur die Web-Oberfläche). Der erste Login von einem neuen "Gerät" verlangt bei Brevo einen per E-Mail zugestellten 6-stelligen Code; danach gilt das Gerät (= die gespeicherte Sitzung) als vertrauenswürdig.

[WARNING]
====
Das erfordert das echte Brevo-Account-Passwort auf dem Server (nicht nur einen API-/SMTP-Schlüssel wie bisher) - eine größere Angriffsfläche. Die Login-/Formular-Interaktion wurde nach bestem Wissen aus der öffentlichen Brevo-Hilfe-Dokumentation entwickelt, aber mangels Testzugang nicht gegen einen echten Account verifiziert - beim ersten Einsatz mit einem Blick auf die bei Fehlern automatisch gespeicherten `error-*.png`-Screenshots nachjustieren.
====

Einrichtung:

. In `deploy/.env`: `BREVO_LOGIN_EMAIL=<login>`
. Passwort ablegen: `echo '<passwort>' > deploy/secrets/brevo_login_password.txt && chmod 644 deploy/secrets/brevo_login_password.txt`
. Einmalig `node_modules` in den gemounteten Ordner installieren (das Playwright-Docker-Image bringt nur den Browser mit, nicht das npm-Paket selbst - der Ordner ist auf den Host gemountet, daher bleibt das dauerhaft erhalten):
+
[source,bash]
----
cd deploy/brevo-ip-updater
docker run --rm -v "$(pwd):/work" -w /work mcr.microsoft.com/playwright:v1.62.1-noble npm install
----
. Einmaliges, interaktives Setup:
+
[source,bash]
----
docker run --rm -it -v "$(pwd):/work" -w /work \
  -e BREVO_LOGIN_EMAIL=<login> -e BREVO_LOGIN_PASSWORD=<passwort> \
  mcr.microsoft.com/playwright:v1.62.1-noble node setup-session.mjs
----
Fragt den per E-Mail zugestellten 6-stelligen Code interaktiv ab und speichert die resultierende Sitzung in `storage-state.json` (nicht committen, siehe `.gitignore`).

Ab dann trägt `check-outbound-ip.sh` bei jeder erkannten IP-Änderung automatisch die neue IP ein (per `docker run` mit derselben gespeicherten Sitzung) und meldet Erfolg/Fehlschlag zusätzlich im ntfy-Push-Text. Schlägt die automatische Eintragung fehl (z.B. weil die gespeicherte Sitzung abgelaufen ist), bleibt die bisherige manuelle Nachtrage-Anleitung der Fallback - `setup-session.mjs` muss dann einmalig erneut ausgeführt werden.

== Troubleshooting

* **Keycloak startet, aber `/realms/konfplan/...` liefert 404**: Realm-Import schlägt bei bereits existierendem Realm mit gleichem Namen aber abweichendem Inhalt NICHT automatisch neu an - `--import-realm` überspringt existierende Realms.
Für einen erzwungenen Reimport das Postgres-Volume der `keycloak`-Datenbank leeren (Datenverlust für alle Keycloak-Änderungen!) oder den Realm manuell über die Admin-Konsole löschen und neu starten.
* **Caddy bekommt kein Zertifikat**: DNS-A-Records prüfen (`dig +short <hostname>` muss die Server-IP liefern) und dass Port 80 tatsächlich von außen erreichbar ist (Cloud-Firewall +
ggf. zusätzlich `ufw`).
* **App kann Keycloak nicht erreichen**: `KC_SERVER_URL`/`KEYCLOAK_INTERNAL_URL` muss auf den Compose-Service-Namen zeigen (`http://keycloak:8080/auth`, mit Pfad `/auth`), nicht auf `localhost` - beide Container laufen im selben Compose-Netzwerk und erreichen sich über den Service-Namen.
* **Subtile Folgefehler, die sich nicht wie ein offensichtlicher Bug anfühlen** (z.B. eine Keycloak-Required-Action wie "Update Password" greift beim Login nicht, obwohl Realm- und User-Konfiguration nachweislich korrekt sind): prüfen, ob die vier `QUARKUS_HTTP_PROXY_*`-Einstellungen im `app`-Service gesetzt sind (siehe `docker-compose.yml`). Ohne sie vertraut Quarkus den `X-Forwarded-*`-Headern von Caddy nicht.
* **App-Log zeigt beim Start `Konnte ... nicht synchronisieren.: ... Connection refused: keycloak/...`** (z.B. gefolgt von dauerhaften `403`-Warnungen des `FailedLoginMetricsPoller`, siehe Monitoring-Grafana.adoc): `app` ist hochgefahren, bevor Keycloaks HTTP-Port tatsächlich erreichbar war - `ProdKeycloakRealmSyncService` läuft beim Start nur einmal, ohne Retry. Der `keycloak`-Service hat dafür einen Healthcheck (`/health/ready` auf dem Management-Port 9000), auf den `app` per `depends_on: ... condition: service_healthy` wartet - sollte das trotzdem auftreten (z.B. sehr langsamer erster Realm-Import), reicht ein `docker compose restart app`, sobald Keycloak vollständig oben ist.
